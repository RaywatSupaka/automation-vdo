# แผนอัปเดตโปรแกรมและ Extension: ภาพสินค้าและการกู้ภาพ

วันที่: 2026-09-05
สถานะ: แผนเท่านั้น — ยังไม่ได้แก้ runtime, เปลี่ยนเวอร์ชัน, สร้างแพ็ก หรือเริ่มงานจริง
ฐานปัจจุบัน: source/manifest และ CURRENT_RELEASE.json ระบุ 0.15.247 Candidate
เลขรุ่นถัดไปที่เสนอ: 0.15.248; ต้องตรวจเลขจริงอีกครั้งก่อนแพ็ก ห้ามอ้างว่าเผยแพร่แล้ว

## 1. เป้าหมายและขอบเขต

- ภาพ Shopee ที่ส่งเข้า AI ต้องเป็นภาพของสินค้าที่เลือก ไม่ใช่ overlay ส่งฟรี/ส่วนลดหรือสินค้าข้างเคียง
- เก็บภาพที่สำเร็จแล้ว และกู้เฉพาะภาพที่ขาดโดยใช้ภาพสำเร็จของงานเดียวกันเป็น reference เมื่อเหมาะสม
- โปรแกรมและ Extension ใช้สถานะ เหตุผล และงบลองใหม่ร่วมกัน ไม่สร้างลูป recovery ซ้อนกัน
- คง provider ที่ผู้ใช้เลือก และคง physical upload/attach/submit/approve/download ของ Google Flow
- เริ่มใช้การกู้ reference กับ Product ก่อน; ทดสอบว่า Story/Drama ยังทำงานเดิม ห้ามนำภาพข้ามฉากเรื่องเล่ามาแทนอัตโนมัติ
- การนำภาพสำเร็จมาอ้างอิงไม่รับประกันว่าภาพใหม่จะถูกต้องหรือผ่านนโยบาย และไม่ใช่เหตุให้ลองคำขอที่ถูกปฏิเสธวน

## 2. หลักฐานจาก source และไฟล์ตัวอย่าง

- browser_extension/content.js: productImages() เก็บ img กว้าง; เส้นทาง card ข้ามตัวกรองขนาด/fixed ส่วน pageProduct() รวม og:image กับภาพทั้ง document และอาจใช้การ์ดแรกก่อนยืนยันสินค้าที่ตรงรายการ
- core/product_manager.py: _download_image() ตรวจชนิดไฟล์ ขนาดไฟล์ และความละเอียดขั้นต่ำ แต่ยังไม่แยก decorative overlay
- ตัวอย่างผู้ใช้ codex-clipboard-3cb7aeaf-a2e7-4496-8a28-a54145fafc35.png: 1200x1200 RGBA, alpha=0 จำนวน 92.81%, ขอบเขตส่วนที่มองเห็น (0,1050,706,1200) เป็นแถบส่งฟรี/ส่วนลดด้านล่าง ไม่ใช่ภาพสินค้าพื้นดำ
- browser_extension/chatgpt.js: generateOneImage() และการกู้ภาพซ้ำยังใช้ pkg.image_urls ซึ่งเป็น reference ต้นฉบับ; runJob() บันทึก partial checkpoint แล้ว แต่ error ของภาพหนึ่งทำให้ออกจาก loop ก่อนทำภาพถัดไป
- การจำแนก third-party refusal ปัจจุบันจำกัด mode=story; Product อาจเข้าพรอมต์ซ่อมเรื่องผู้ใหญ่/ไม่มีความรุนแรงที่ไม่ตรงเหตุผล
- checkpoint image URLs ของ Product มี index และ route งานเดิมอยู่แล้วใน core/local_bridge.py; ต้องใช้ไฟล์ที่บันทึกสำเร็จ ไม่ใช้ลิงก์ชั่วคราวในหน้าเว็บเป็นแหล่งหลัก
- การแนบ reference มีเพดาน 3 ภาพและมี helper ใช้รูปเก่าที่แนบไว้แล้ว จึงเปลี่ยน URL อย่างเดียวไม่ได้รับประกันว่าเว็บใช้ donor จริง
- ui/main_window.py และ core/product_pipeline.py มี recovery ชั้นโปรแกรมอยู่แล้ว ต้องไม่เพิ่ม budget อีกชุดแข่งกับ Extension

## 3. ระยะ A — กรองภาพ Shopee ก่อนเข้า AI

### Extension

1. ยืนยัน product/shop identity ของหน้าหรือการ์ดเป้าหมายก่อนเลือกรูป ห้ามหยิบการ์ดแนะนำแรกโดยไม่ตรงสินค้าที่ร้องขอ
2. ให้ภาพจากแกลเลอรีของสินค้านั้นมาก่อน และคัดออกเฉพาะชั้นตกแต่งที่มีหลักฐาน DOM/บทบาท/ตำแหน่งร่วมกัน
3. เก็บข้อมูลประกอบที่จำเป็นก่อนแปลงเป็น URL เช่น ประเภทแหล่งภาพ ขนาด ลำดับในแกลเลอรี และเหตุผลคัดออก; ไม่เก็บ HTML ทั้งหน้า/ข้อมูลบัญชี
4. ห้ามใช้ position:absolute, คำในชื่อไฟล์, คำว่าโลโก้/ส่งฟรี หรือขนาดเพียงอย่างเดียวตัดสิน
5. ต้องดู DOM ตัวอย่างจริงก่อนกำหนด selector ใหม่ ห้ามเดาชื่อ class แล้วทำเป็นตัวกรองถาวร

### โปรแกรม

1. ตรวจไฟล์ที่ดาวน์โหลดซ้ำด้วย alpha coverage, bounding box และหลักฐานชนิดภาพจาก Extension
2. ตัวอย่าง overlay ที่ผู้ใช้ยืนยันใช้เป็น regression fixture; ความโปร่งใสอย่างเดียวไม่พอ เพราะภาพสินค้าตัดพื้นหลังก็โปร่งใสได้
3. ผลตัดสินมีสามประเภท: ใช้เป็นภาพสินค้า / ไม่ใช้เพราะยืนยันว่าเป็น overlay / รอตรวจสอบ
4. เก็บรูปต้นฉบับและเหตุผลไว้; แยกรายการภาพที่อนุญาตให้ส่ง AI โดยไม่ลบไฟล์หรือทำลาย checkpoint
5. งานเก่าตรวจใหม่เฉพาะก่อนเริ่ม/ทำต่อและเมื่อไม่มี worker กำลังใช้ชุดภาพนั้น ใช้ revision guard; ไม่เปลี่ยน source ของงานที่กำลังสร้างหรือสร้าง Final แล้วเงียบ ๆ
6. ถ้าไม่เหลือภาพสินค้าที่ใช้ได้ ให้แจ้งเลือกภาพ ไม่เติมรูปอื่นที่ไม่ตรงสินค้าและไม่ส่ง AI แบบไม่มี reference

## 4. ระยะ B — จำแนกข้อผิดพลาดและคุมสิทธิ์ลองใหม่ร่วมกัน

รหัสและโครงสร้างในส่วนนี้เป็นข้อเสนอ ต้องกำหนดสัญญาและ tests ก่อนนำไปใช้จริง

- ยังสร้าง/เข้าคิว/ผลครั้งก่อนยังไม่ชัด: เฝ้าดูรอบเดิม ห้ามส่งซ้ำหรือเปลี่ยน reference
- กดส่งแล้วไม่มีการยืนยัน: เก็บสถานะไม่ทราบผลและตรวจหลักฐานเดิม ไม่ถือเป็นความล้มเหลวที่อนุญาตให้สร้างซ้ำ
- ภาพสร้างแล้วแต่ดาวน์โหลดไม่สำเร็จ: กู้การดาวน์โหลดภาพเดิม ไม่เรียกสร้างใหม่
- ความล้มเหลวทั่วไปที่ยืนยันว่ารอบเดิมจบแล้ว: อนุญาตกู้ตามงบรายภาพ
- Policy/third-party refusal: เก็บเหตุผลจริง หยุดการลองแบบเดิม และไม่ใช้ donor เพื่อส่งคำขอเดิมหลบการปฏิเสธ; เสนอภาพที่มีสิทธิ์ใช้ประกอบคลิป/การแก้เนื้อหาอย่างเหมาะสมแยกต่างหาก
- Login/CAPTCHA/เครดิต/permission: รอการจัดการของผู้ใช้ ไม่เดินข้ามไปสร้างภาพอื่น
- Cancelled: หยุดและรักษาไฟล์ที่สำเร็จ ผลตอบกลับรอบเก่าห้ามปลุกงานใหม่

ข้อกำหนด budget:

1. หนึ่งภาพมี initial generation 1 ครั้ง และ recovery ที่อนุญาตเพิ่มไม่เกิน 1 ครั้ง โดยรวมทุกชั้น รวม duplicate-result retry
2. จองสิทธิ์แบบ atomic/durable ก่อน dispatch และบันทึก request/slot/analysis revision/reference identity
3. Resume, Desktop recovery, โหลด Extension หรือเปิด EXE ใหม่ต้องไม่รีเซ็ตสิทธิ์
4. ถ้าล่มหลัง dispatch แต่ก่อนรับผล ให้ reconcile แบบอ่านอย่างเดียว ไม่แจกสิทธิ์ส่งใหม่
5. ข้อผิดพลาดก่อนส่งที่พิสูจน์ว่าไม่มี dispatch จัดการแยกจากการสร้างภาพ ห้ามคาดเดาว่าไม่ส่งแล้วเริ่มซ้ำ
6. โปรแกรมเป็นแหล่งสถานะถาวร Extension เป็นผู้ปฏิบัติหนึ่งราย ไม่เพิ่ม scheduler หรือ worker แข่งกัน

## 5. ระยะ C — กู้ภาพที่ขาดด้วยภาพสำเร็จของงานเดิม

### กรณีภาพ 2 สำเร็จ แต่ภาพ 3 ล้มเหลวทั่วไป

1. ยืนยันว่าภาพ 2 เปิดอ่านได้และ checkpoint ได้รับ ACK แล้ว ตรง Job/ชุดวิเคราะห์ และไม่ใช่ overlay
2. ใช้ URL checkpoint ภาพ 2 เป็น reference พร้อมพรอมต์ของภาพ 3 ไม่ใช่พรอมต์ของภาพ 2
3. ระบุสิ่งที่แก้เฉพาะฉาก/องค์ประกอบที่ต้องการ โดยไม่แต่งรูปร่าง คุณสมบัติ หรืออุปกรณ์ของสินค้า
4. เลือกชุด reference อย่างชัดเจน ไม่ต่อ donor ท้าย 3 รูปจนถูกตัดทิ้ง และต้องพิสูจน์ว่า Composer แนบ donor จริง ไม่ใช่รูปเดิมที่ค้างอยู่
5. ใช้เส้นทาง attach/send เดิมหนึ่งครั้ง เฉพาะ recovery ที่มีสิทธิ์; ถ้าพิสูจน์รูปไม่ได้ให้หยุด ไม่เปิดภาพ preview/อัปโหลดซ้ำวน
6. รับเฉพาะผลใหม่ของ attempt นั้น ตรวจไฟล์และภาพซ้ำ บันทึกช่อง 3 ก่อนส่งต่อ ห้ามทำ generatedImages[2] = generatedImages[1] แล้วอ้างว่าสร้างภาพใหม่

### กรณีภาพ 1 ล้มก่อนมี donor

- พักช่อง 1 เฉพาะ terminal non-policy ที่อนุญาต แล้วทำช่อง 2 และ 3 ตามลำดับ
- เมื่อจบรอบแรก กลับมากู้เฉพาะช่องที่ขาดและยังมีสิทธิ์ โดยใช้ภาพที่สำเร็จและบันทึกแล้วจากรอบแรก
- คง mapping ช่องภาพ -> image prompt -> Flow prompt -> บทพูด ไม่บีบ array จนภาพ 2 กลายเป็นภาพ 1
- ไม่ใช้ภาพที่เพิ่งกู้ได้เป็น donor ต่อทอดไม่จำกัด และไม่ทำรอบ deferred เพิ่มเรื่อย ๆ
- ถ้าทุกภาพล้มและไม่มี donor ให้จบด้วยทางเลือกสำรอง/รอผู้ใช้ ไม่เริ่มงานใหม่ทั้งหมด

### ขอบเขตงานแก้

- วาง recovery scheduling, durable budget และ reference selection แยกทดสอบก่อนรวม
- ถ้าต้องเปลี่ยน helper พิสูจน์ attachment identity ให้ทำเป็นงานย่อยมี real-DOM evidence และ regression เฉพาะ ไม่ปิด guard ใช้รูปเดิมของ Gemini/ChatGPT ทั้งระบบ
- ไม่เปลี่ยนการคลิก Google Flow, ตัวอ่าน JSON หรือรูปแบบ Voice/Subtitle ในชุดนี้

## 6. ทางสำรองใช้ภาพเดิมประกอบคลิป

- เป็นความสามารถแยกจาก “AI สร้างภาพใหม่” และแยกจาก Flow policy fallback เดิม
- ให้ตั้งค่าหรือยืนยันอย่างชัดเจนก่อนใช้อัตโนมัติ; ค่าเริ่มต้นสำหรับงานเก่าคือไม่เปิดทางสำรองใหม่เงียบ ๆ
- เลือกเฉพาะภาพที่เหมาะสมและมีสิทธิ์ใช้ของสินค้านั้น ไม่เปลี่ยนเป็นสินค้าคนละแบบและไม่ลบไฟล์ที่สำเร็จ
- จัดเก็บ ordered image slots พร้อม origin เช่น generated / recovered_from_reference / reused_existing / original_product และเหตุผลของแต่ละช่อง; ชื่อ field จริงต้องกำหนดตอนออกแบบ schema
- donor ไม่เพิ่มจำนวนภาพสร้างใหม่; นับเพิ่มเฉพาะภาพใหม่ที่บันทึกสำเร็จ การใช้ภาพเดิมต้องแสดงตามจริง
- โปรแกรมประกอบ local motion ของช่องสำรอง ไม่ส่งคำขอที่ถูกปฏิเสธไปลองกับ provider อื่นอัตโนมัติ
- ตรวจความสอดคล้องกับบทพูดและคงหมายเลขช่อง อัปเดต readiness/preview/Final ให้รองรับ source type อย่างถูกต้อง ไม่ปลอม generated_images ให้ครบ
- ไม่สร้างไฟล์วิดีโอซ้ำแล้วอ้างว่าเป็นคนละ Flow shot; คงการตรวจ duplicate clip และรายงานจำนวน real Flow/local แยกกัน
- ถ้าไม่มีภาพที่เหมาะสม ให้หยุดพร้อมภาพที่เสร็จแล้วและเหตุผล ไม่แจ้ง Final สำเร็จ

## 7. UI และ Log ที่ต้องเพิ่ม

- แสดงจำนวนภาพสินค้าที่ใช้ได้, overlay ที่ไม่นำไปใช้ และภาพที่รอตรวจ พร้อมดูเหตุผล/เลือกภาพเอง
- แสดงสถานะรายช่อง: กำลังสร้าง / บันทึกแล้ว / รอกู้ / กู้ด้วยภาพ N / ใช้ภาพเดิม / ต้องจัดการเอง
- ปุ่มดู Log/คัดลอก Log รวม Job, slot, stage, error category, donor index, attempt/budget และผล checkpoint
- ตัวอย่าง: “ไม่นำภาพโปรโมชัน Shopee ไปใช้”, “กู้ภาพ 3 ด้วยภาพอ้างอิง 2 • ครั้งที่ 1/1”, “ภาพ 3 ใช้ภาพเดิมประกอบคลิป ไม่ใช่ภาพ AI ใหม่”
- Log ทุก transition ที่สำคัญแต่ deduplicate heartbeat; ไม่ใส่ token, cookie, credentials, signed URL หรือ base64 รูปลง Log
- งานสำเร็จต้องอิงไฟล์และ receipt จริง; popup ที่ผู้ใช้ย่อไว้ต้องไม่เปิดกลับจาก heartbeat

## 8. แผนที่ไฟล์สำหรับลงมือ

- browser_extension/content.js: การเลือกภาพ/สินค้าและข้อมูลประกอบ overlay
- browser_extension/chatgpt.js: จำแนก image failure, กู้เฉพาะช่อง และพิสูจน์ reference ใน recovery
- browser_extension/background.js: ขนส่ง metadata/checkpoint/receipt เท่าที่จำเป็น ไม่แก้ physical Flow
- core/product_manager.py: source selection, checkpoint และข้อมูลภาพรายช่อง
- core/local_bridge.py: สัญญาข้อมูลและ validation ตาม Job/run/revision/เวอร์ชัน
- core/product_pipeline.py และเฉพาะ worker ที่เกี่ยวข้องใน ui/main_window.py: shared recovery budget, readiness, resume และ completion
- web_ui/: แสดงสถานะ/เหตุผล/ตัวเลือกสำรองเฉพาะจุด ไม่ยกเครื่อง UI ทั้งโปรแกรม
- tests/: เพิ่ม executable behavior tests ไม่พึ่งตรวจ string ใน source อย่างเดียว

## 9. Acceptance tests ก่อนออกแพ็ก

1. Overlay ตัวอย่างถูกคัดออก แต่สินค้าพื้นหลังโปร่งใส สินค้าดำ บรรจุภัณฑ์มีข้อความ และรูปสินค้าที่มีแถบโปรโมชันฝังรวมไม่ถูกทิ้งด้วยกฎกว้าง
2. การ์ดแนะนำ/ภาพรีวิว/ภาพสินค้าคนละ ID ไม่ถูกนำมาเป็น reference; รูปซ้ำหลายความละเอียดไม่เบียดรูปสินค้าจริง
3. งานเก่าตัด overlay ออกจากชุดส่ง AI ได้โดยไม่ลบไฟล์ ไม่แก้ active run และไม่ invalidate Final เงียบ ๆ
4. รูป 1–3 สำเร็จปกติ: ไม่มี recovery/reference replacement เพิ่ม
5. รูป 3 ล้มหลังรูป 2 สำเร็จ: แนบรูป 2 จริง สร้างใหม่ไม่เกินหนึ่งครั้ง บันทึกเป็นช่อง 3 และไม่ทำช่อง 1–2 ซ้ำ
6. รูป 1 ล้ม -> รูป 2/3 สำเร็จ -> กู้รูป 1 ได้เพียงหนึ่งครั้ง; prompts/บทพูด/Flow slots ไม่สลับ
7. ทุกภาพล้มไม่มี donor / donor ต่าง Job / checkpoint ไม่ ACK / ไฟล์เสีย / revision เก่า: ปฏิเสธ recovery อย่างมีเหตุผล
8. Refusal, login, credit, cancellation, send-unconfirmed และ generation ยังไม่จบ: ไม่เข้ากู้แบบสร้างซ้ำ
9. รูปเสร็จแต่ download ล้ม: กู้ไฟล์เดิม ไม่สร้างภาพใหม่
10. Crash หลัง dispatch, callback ซ้ำ/รอบเก่า, Desktop recovery และเปิด EXE ใหม่: ไม่คืน retry budget ไม่ส่งซ้ำ
11. ภาพใหม่ซ้ำกับ donor: ไม่เพิ่ม generated count และไม่เปิดลูป nested retries
12. ทางสำรองภาพเดิม: ต้องได้รับอนุญาต, UI/readiness/Final รายงาน origin และ Flow/local counts ตามจริง
13. ChatGPT และ Gemini เส้นทางปกติ, Story/Drama, cancel/resume, queue และ popup เดิมยังผ่าน

## 10. วิธีปล่อยอัปเดตและข้อห้าม

1. เก็บ baseline source ปัจจุบันและผลทดสอบก่อนแก้ ห้าม restore จาก Git HEAD หรือคัดลอกแพ็กเก่าทับ source
2. ทำระยะ A -> B -> C ทีละส่วน พร้อม targeted tests; การสำรองภาพเดิมอยู่หลังสัญญาสถานะชัดเจน ไม่เปิดพร้อมกันโดยไม่ทดสอบ
3. แยกการเปลี่ยนแต่ละชั้นเป็นชุดย่อยตรวจย้อนกลับได้ และไม่รวมการเปลี่ยน attach+submit+monitor+download หลายอย่างในรุ่นเดียว
4. รัน full suite และ isolated bridge/Extension harness หลัง targeted tests ผ่าน
5. ตรวจปุ่ม/status ผ่าน SmartFlow AI.exe; งานเว็บจริงต้องจบด้วย SmartFlow Extension ไม่ใช่ Codex คลิกแทน
6. ไม่ใช้การควบคุมหน้าต่าง Windows รบกวนผู้ใช้ เฝ้าดูผ่าน Log/การอ่านเว็บตามที่ผู้ใช้ยอมรับ ไม่เริ่มงานซ้ำจากอาการนิ่ง
7. ทดสอบเสร็จปิดเฉพาะ helper/backend/browser/window ที่ Codex เปิดเพื่อเทส หลังยืนยันว่าไม่มี active job; ห้ามปิดโปรแกรมหรืองานที่ผู้ใช้เปิดไว้
8. ก่อนแพ็กตรวจเลขเวอร์ชันล่าสุดจริง ซิงก์ manifest, Bridge required version, helper build และข้อมูลติดตั้ง; อัปเดต blueprints/สมุด regression ให้ตรงสิ่งที่แก้จริง
9. แพ็กจาก browser_extension/ เท่านั้น ตรวจ service worker/JS syntax และไฟล์ source-folder-ZIP ตรงกันทุกไฟล์ พร้อม SHA256
10. ส่ง path โฟลเดอร์และ ZIP ที่มีอยู่จริง ระบุให้ชัดว่าต้องติดตั้งรุ่นไหนและเปิด EXE ใหม่เมื่อไม่มีงานกำลังรัน; ไม่อ้างแพ็กเก่าเป็นแพ็กใหม่
11. ให้ผู้ใช้ติดตั้งก่อน installed smoke และแยกผล unit/harness ออกจากผล E2E จริง ไม่รับประกัน 100% หรือรายงานเปอร์เซ็นต์ดีขึ้นโดยไม่มีผลวัด

## 11. เกณฑ์จบงาน

- ภาพโปรโมชันไม่ถูกส่งเข้า AI ในกรณีทดสอบที่ยืนยันแล้ว โดยไม่ทำให้รูปสินค้าจริงหาย
- ภาพที่สำเร็จไม่ถูกสร้างซ้ำ กู้เฉพาะช่องที่ขาดตาม budget และไม่มีคลิก/อัปโหลด/รีเฟรชวน
- สถานะโปรแกรมตรงกับ Extension และอธิบายภาพใหม่/ภาพเดิม/Flow/local ตามจริง
- มีแพ็กคู่เวอร์ชัน ตรวจติดตั้ง service worker ได้ และผลทดสอบทั้งเส้นทางปกติกับ recovery/fallback ตามขอบเขตที่เปิดใช้
- เก็บหลักฐานข้อจำกัดที่ยังเหลือและปิดสิ่งที่เปิดเทส โดยไม่แตะงานผู้ใช้ที่กำลังรัน
