# แผนตั้งค่าก่อนโพสต์ Shopee — ลงมือพัฒนาแล้วตามการอนุมัติถัดมา

วันที่: 2026-09-19

อัปเดตหลังผู้ใช้สั่ง **“อัพเกรดได้เลย”**: ดำเนิน A–E ใน source แล้ว เพิ่มค่าเริ่มต้น/รายคลิป/ตรวจสวิตช์/กู้พอร์ตเครื่องเดิม และทดสอบแบบไม่เผยแพร่ รายละเอียดล่าสุด [รายงานผล](../reports/shopee-post-options-20260919/README.md) ข้อความ “ยังไม่พัฒนา” ด้านล่างเป็นสถานะตอนวางแผนเดิม ไม่ใช่สถานะปัจจุบัน การเผยแพร่จริงเพิ่มเติมและการทดสอบคิวหลายคลิปยังต้องขออนุญาตใหม่

สถานะ: ผู้ใช้ยืนยัน **“ทดสอบและบันทึกแผนก่อน”** รอบนี้ไม่มีการแก้ source โปรแกรม/Extension ไม่มีการกดโพสต์จริง ไม่มีการแก้โพสต์เดิม และไม่มี installer/restart ผู้ใช้

## 1. เป้าหมาย

หน้า **ระบบ → โพสนายหน้า Shopee** ให้ผู้ใช้ตั้งค่าก่อนเผยแพร่ได้ โดยค่าเริ่มต้นตามคำขอ:

| ตัวเลือก | ค่าเริ่มต้น | พฤติกรรม |
|---|---|---|
| อนุญาตให้นำเนื้อหาไปใช้ซ้ำหรือเผยแพร่ต่อ | ปิด | ต้องตรวจว่า OFF จริงก่อน Post |
| เพิ่มป้ายกำกับ AI ไปยังเนื้อหา | เปิด | ต้องตรวจว่า ON จริงก่อน Post |

ยังคงส่งเฉพาะวิดีโอ ไม่ส่งรูปปก ไม่เปิด cover picker ไม่สร้าง Final ใหม่ การแชร์ต่อ Facebook/WhatsApp ยังคงปิดตามสัญญาเดิม; “บันทึกลงในโทรศัพท์” ไม่ใช่สวิตช์ที่ทดสอบเปลี่ยนในรอบนี้

## 2. สิ่งที่พบในโค้ดปัจจุบัน

- `core/shopee_posting/workflow.py::run` เรียก `screenshot_toggle(...ai_generated_toggle, True)` อยู่แล้ว แต่ยังไม่จัดการ `allow_reuse_toggle`
- `device.py::visual_green` อนุญาตเฉพาะ AI/WhatsApp/Facebook ไม่มี reuse จึงเพิ่มแค่คำสั่งคลิก reuse อย่างเดียวไม่ได้ ต้องเพิ่มวิธีตรวจผลของมันด้วย
- `publish.py::publish_current` ตรวจ AI ว่าเปิดและแชร์ต่อว่าปิดก่อน Post แต่ยังไม่ตรวจ reuse จึงอาจเผยแพร่ทั้งที่ reuse ยังเปิดตามค่าเริ่มต้นของ Shopee
- `store.py::edit` รับเพียง caption/product_url/removed; queue และ publish_intent ยังไม่เก็บค่าทั้งสองแบบรายคลิป
- `web_ui/shopee_posting.js` ยังไม่มีหน้าตั้งค่าสองตัวเลือกนี้ และข้อความยืนยันยังเขียน AI เปิดแบบคงที่
- `workflow.py::verify_result` ต้องเห็นป้าย AI เสมอ หากทำให้ผู้ใช้เลือก AI ได้ ต้องเปลี่ยนการตรวจผลให้ยึดค่าในงาน มิฉะนั้นงานที่เลือกปิดจะถูกตีเป็น unknown แม้โพสต์สำเร็จ

## 3. ผลทดสอบมือถือจริง — ไม่เผยแพร่

Samsung S25 Ultra / Android16 / Shopee ภาษาไทย เครื่องเดิมที่ยืนยัน hardware identity ได้ ทดสอบโดยเปิดคลิป Anata เดิมจากอัลบั้มเดิม ไม่โอนไฟล์เพิ่ม ไม่แก้ caption/สินค้า และไม่เรียก publisher

1. ก่อนปรับ: reuse สีเขียวเปิด, AI สีเทาปิด, WhatsApp เปิด, Facebook ปิด
2. ตรวจ resource และข้อความกำกับตรงกัน แล้วกด `allow_reuse_toggle` **หนึ่งครั้ง** ผลเป็นสีเทา OFF ไม่มี confirmation dialog แทรก
3. ใช้ตัวตรวจเดิมเปิด `ai_generated_toggle` **หนึ่งครั้ง** ผลเป็นสีเขียว ON
4. เรียกตรวจ/ตั้ง AI เป็น ON อีกรอบ **ไม่เกิดการคลิกเพิ่ม** (สองคำสั่งตั้งค่า รวมหนึ่ง gesture) จึงไม่สลับกลับเป็น OFF
5. XML ของ reuse และ AI ยังคง `checkable=false`, `checked=false`, `clickable=false` ทั้งก่อนและหลัง แม้ภาพแสดงสถานะเปลี่ยนจริง ห้ามใช้ checked=false เป็นหลักฐานปิด
6. ออกจาก composer → editor → ละทิ้งการตั้งค่าของ session ทดลองที่สร้างเอง → ออกจากกล้อง กลับหน้าเดิม ไม่บันทึก draft ไม่แตะ Post วิดีโอ/ปก/โพสต์เดิมคงอยู่

ขอบเขตที่พิสูจน์: คลิกสองสวิตช์และตรวจผลบนมือถือจริงใน session ทดลอง ไม่ใช่ทดสอบค่า server หลังเผยแพร่ ไม่ใช่ UI settings ใหม่ของ Desktop เพราะยังไม่สร้าง และไม่ใช่หลักฐานว่าค่าจะจำข้ามการเปิด composer ใหม่ได้

## 4. UX/UI ที่จะเพิ่ม

### ค่าเริ่มต้นของงานใหม่

เพิ่มกล่อง **“ตัวเลือกก่อนโพสต์”** เหนือคิว พร้อมสวิตช์สองตัว ข้อความเปิด/ปิดชัดเจน ไม่อาศัยสีอย่างเดียว:

- อนุญาตให้นำเนื้อหาไปใช้ซ้ำ/เผยแพร่ต่อ — ปิด
- เพิ่มป้ายกำกับ AI — เปิด
- ปุ่ม **บันทึกเป็นค่าเริ่มต้น** และคำอธิบายว่าใช้เฉพาะงานที่เพิ่มเข้าคิวหลังจากนี้
- แสดงคำแนะนำว่าคลิปจาก AI ควรเปิดป้ายกำกับ การเปลี่ยน AI ต้องเป็นการเลือกอย่างชัดเจน ไม่ปิดอัตโนมัติเพียงเพราะหาปุ่มไม่เจอ

### รายคลิปในคิว

- แสดงสองตัวเลือกในร่างแต่ละคลิป ปุ่มบันทึกรวมแคปชัน/ลิงก์/ตัวเลือก
- มีปุ่ม **ใช้ค่าด้านบนกับงานที่ติ๊กเลือก** พร้อมจำนวนงาน ช่วยแก้คิวเดิมอย่างชัดเจน ไม่เปลี่ยนทุกงานเงียบ ๆ
- แก้ได้เฉพาะ draft/review/prepared ที่ยังไม่มี publish_intent; queued/active/send_pending/processing/published/unknown ล็อกไว้
- ก่อนเริ่ม ถ้ามีค่าที่ยังไม่บันทึกให้เตือนเหมือน caption เดิม; confirmation แสดงบัญชี จำนวนคลิป และสรุปค่าที่ใช้จริง หากค่าคละกันแสดงจำนวนตามกลุ่ม ไม่อ้างว่าทุกคลิปเหมือนกัน
- สถานะทำงานแสดง “ตรวจแล้ว: ใช้ซ้ำปิด • ป้าย AI เปิด” จากผลที่ตรวจจริง ไม่แสดงเพียงค่าที่ผู้ใช้สั่ง

## 5. การเก็บค่าและป้องกันงานเปลี่ยนกลางทาง

เสนอ `post_options` แบบ versioned (`schema=1`) มี booleanจริง `allow_reuse=false`, `ai_label=true`; ห้ามแปลง string `"false"` เป็น true หรือรับ null แบบเงียบ

1. เก็บ defaults แยกจาก snapshot ของแต่ละแถวใน PostingStore เดิม ไม่เก็บเฉพาะ browser storage
2. เมื่อเพิ่มร่างให้คัดลอก defaults ลงแถวทันที การเปลี่ยน defaults ภายหลังไม่เปลี่ยนคิวที่มีแล้ว
3. ร่าง legacy ที่ยังไม่เคยส่ง แสดงค่าปลอดภัยตามคำขอและให้เห็นก่อนเริ่ม; บันทึก migration เฉพาะ unsent row อย่าง atomic ห้ามแตะผล posted หรือ unknown เก่า
4. ตอน start ยืนยัน revision/บัญชี/มือถือและตรึงค่ารายงาน ภายใต้ lock เดียวกับ claim queue
5. publish_intent เก็บ snapshot ตัวเลือก + หลักฐานก่อนส่งไว้ด้วย การตรวจหลังโพสต์ยึด snapshot นี้ ไม่อ่าน defaults ล่าสุด
6. Recovery ใช้ค่าที่ตรึงไว้เดิม ไม่กลับค่าเริ่มต้นหลัง restart และไม่ล้าง intent เพื่อให้ส่งใหม่

## 6. ลอจิกมือถือที่จะพัฒนา

ลำดับ: เตรียมวิดีโอ → แคปชัน/สินค้า → ตั้งตัวเลือก → ตรวจทั้งหมดอีกครั้ง → durable intent → Postครั้งเดียว → ตรวจผลเดิม

สำหรับแต่ละสวิตช์:

1. ตรวจเครื่อง/แอป/หน้าก่อนโพสต์และชื่อกำกับตรงกับ resource ปัจจุบัน รอ animation ให้ตำแหน่งนิ่ง
2. หาก semantic checked ใช้งานได้จริงใน UI รุ่นใหม่ให้ใช้ค่าที่พิสูจน์แล้ว; รุ่นที่ทดสอบนี้ใช้ screenshot เฉพาะพื้นที่สวิตช์ร่วมกับกรอบปุ่มจาก XML
3. ต้องเห็นสวิตช์ครบ ไม่ถูก popup/keyboard บัง ตรวจสีและตำแหน่งปุ่มกลมร่วมกันเพื่อลดการเข้าใจหน้าขาวว่างว่า OFF; ไม่ hardcode ตำแหน่งหน้าจอ
4. อ่านก่อน ถ้าตรงค่าที่ต้องการแล้ว **ไม่คลิก** ถ้าไม่ตรงคลิกเพียงครั้งเดียวแล้วรอผลนิ่ง อ่านใหม่
5. ถ้าอ่านไม่ได้ ตำแหน่งเปลี่ยน หรือขาดการตอบรับ ห้าม blind toggle กลับไปมา ให้ re-read ก่อน; หากยังไม่ยืนยันให้พักก่อน Post พร้อมบอกชื่อสวิตช์ที่ไม่ผ่าน
6. หลังตั้งครบตรวจ reuse/AI/แชร์ต่ออีกครั้ง และทำ preflight สดใกล้จังหวะ Post ป้องกันผู้ใช้หรือ Shopee เปลี่ยนค่าระหว่างขั้น
7. บันทึก observed state/screenshot/XML และเวลาตรวจแยกจาก requested state ไม่อ้างว่า backendยอมรับจนยังไม่ได้เผยแพร่
8. หลัง Post ถ้า AI เปิดให้ตรวจป้าย AI ในผลเดิม; ถ้า AI ปิดต้องไม่รอ label ON ที่ไม่ควรมี ส่วน reuse ยังไม่มีหลักฐาน serverหลังโพสต์จากรอบนี้ จึงไม่อ้างว่าตรวจสำเร็จหลังโพสต์ได้ด้วยภาพก่อนส่งเพียงอย่างเดียว

มือถือมีตัวเลือก/หน้าตาใหม่ที่ตรวจไม่ได้ให้ reviewก่อนส่ง รักษา at-most-once Post และ unknown guardเดิม ไม่ใช้ toggle test ไปสร้าง post retry

## 7. ไฟล์ที่คาดว่าจะเปลี่ยนเมื่ออนุมัติ

- `core/shopee_posting/store.py`: options/defaults/revision/intent snapshot/legacy migration
- `core/shopee_posting/service.py`: actionsตั้งค่าและใช้กับร่างที่เลือก, validation, frozen start
- `core/shopee_posting/device.py`: reuse state reader + evidence/visibility/stability guards
- `core/shopee_posting/workflow.py`: apply actual per-row settings และ conditional result verification
- `core/shopee_posting/publish.py`: ตรวจค่าทั้งคู่ก่อน durable single Post
- `web_ui/index.html`, `shopee_posting.js`, `shopee_posting.css`, `ui/main_window.py`: UIและaction routing
- tests ของ store/device/publisher/actual-source UI; blueprint/release reportหลังพัฒนา
- ไม่แก้ `browser_extension/` และไม่เปลี่ยน ChatGPT/Gemini/Flow/Meta generation

## 8. เกณฑ์ผ่านก่อนส่งมอบ

- save/reopen defaultsยังอยู่, new draft snapshotถูก, existing draftไม่เปลี่ยนเอง, selected-only apply, stale revisionและactive rowถูกปฏิเสธ
- AI/reuseทั้งON/OFF/ตรงอยู่แล้ว/อ่านไม่ได้; สีเทาแต่XMLfalse, สีเขียวแต่XMLfalse; unsupported theme/overlay/animationและทรานสปอร์ตหลุด ห้ามคลิกซ้ำโดยไม่รู้ผล
- ไม่คลิก Postเมื่อสวิตช์ใดไม่ตรง, ยังไม่มีintentเมื่อpreflightไม่ผ่าน; หลังintentแล้วunknownห้ามเริ่มใหม่
- UI1440/600/360px, keyboard navigation, dirty optionsไม่ถูกpollทับ, confirmationสะท้อนค่าจริง
- ทดสอบมือถือจริงแบบไม่โพสต์อีกรอบหลัง implementation และทดสอบบัญชี/ความคงอยู่ข้ามขั้น; หากจะทดสอบเผยแพร่เพิ่มเติม ต้องขออนุญาตใหม่ ไม่ถือสิทธิ์หนึ่งโพสต์เดิมว่าใช้ได้ตลอด
- targetedก่อน full suite แล้ว audit Extension unchanged; EXE-backed UIแยก instanceและเก็บกวาดเฉพาะของเรา

## 9. สิ่งที่ยังไม่ทำ

ยังไม่ได้เพิ่มสองสวิตช์ในโปรแกรม ยังไม่ได้เปลี่ยน worker/defaults/intent หรือทดสอบ UIของฟังก์ชันใหม่ ยังไม่ได้พิสูจน์ reuseฝั่งserverหลังโพสต์ ไม่มีการปิดreuseของโพสต์ Anata เดิมย้อนหลัง คิวจริงยังมี publishedเดิมหนึ่งแถว

## 10. แผนอัปเกรดพร้อมลงมือ — ลำดับพัฒนา

เพิ่มเติมตามคำขอ “วางแผนอัปเกรดโปรแกรม” หลังทดสอบเสร็จ ขอบเขตคือ **โมดูลโพสต์ Shopee** ไม่รวมระบบสมาชิก/Token/เซิร์ฟเวอร์อัปเดต/ตัวติดตั้ง หรือการแก้การสร้างคลิปใน Extension สถานะยังเป็นแผน ไม่อนุมัติให้เผยแพร่เพิ่มโดยอัตโนมัติ

### ระยะ A — สัญญาข้อมูลและป้องกันค่าเปลี่ยนกลางงาน (ทำก่อน UI)

1. เพิ่มตัวตรวจ `post_options` เวอร์ชัน1 พร้อมค่าเริ่มต้น reuseปิด/AIเปิด และ errorแยกสำหรับข้อมูลไม่ถูกต้อง
2. เพิ่มการบันทึก defaults, saveรายคลิป, applyเฉพาะแถวที่เลือก โดยทุก actionตรวจ revisionและล็อกเดียวกับการเริ่ม worker; applyเป็นธุรกรรมเดียว หากมีแถว active/unknown/ถูกแก้ระหว่างทาง ให้ปฏิเสธทั้งชุด ไม่สำเร็จครึ่งเดียว
3. แยก `requested_options` ที่บันทึกไว้, `observed_options` จากจอ, และ snapshotใน publish_intent ไม่ใช้ค่าเดียวแทนทั้งสามความหมาย
4. ตรึง options/account/device/media identity ตอนเริ่มแต่ละแถว ก่อนกด Post ตรวจ snapshot/revisionยังตรง ห้าม pollหรือหน้าต่างอีกอันเปลี่ยนค่าขณะทำงาน
5. อ่านคิวเก่าได้โดยไม่เขียนประวัติทับ: published/unknownห้าม migrateค่าให้เสมือนเคยใช้อยู่ ร่าง unsentแสดงค่าที่จะใช้และบันทึกก่อนเริ่ม หากโครงสร้างไม่รองรับให้พักอย่างชัดเจน

**ผ่านระยะ A เมื่อ:** ทดสอบบันทึก/เปิดใหม่, true/falseจริง, defaultsใหม่ไม่กระทบร่างเดิม, applyหลายแถวแบบatomic, concurrent start/edit, restartและไฟล์เสีย โดยไม่เปลี่ยนแถวที่เผยแพร่แล้ว

### ระยะ B — หน้าตั้งค่าที่ใช้งานง่าย

ตำแหน่งหน้าจอ: **เลือกคลิป → ตัวเลือกก่อนโพสต์ → คิวพร้อมแคปชัน/ลิงก์ → ยืนยันบัญชีและเริ่ม**

- การ์ดตั้งค่าสองสวิตช์ พร้อมคำว่า เปิด/ปิด และคำอธิบายผล ไม่ใช้ dropdown
- ปุ่ม “บันทึกเป็นค่าเริ่มต้น” กับ “ใช้กับคลิปที่ติ๊กเลือก” แยกกัน เพื่อไม่ให้ผู้ใช้เข้าใจว่าบันทึก defaultsแล้วคิวเก่าเปลี่ยนตาม
- แต่ละแถวมีสรุป เช่น “ใช้ซ้ำ: ปิด • ป้าย AI: เปิด” และปรับเฉพาะแถวได้เมื่อยังไม่เริ่ม
- แสดงสถานะ “ยังไม่บันทึก” เมื่อแก้ และกันเริ่มคิวจนบันทึกครบ; refresh/pollไม่ล้างค่าที่กำลังพิมพ์หรือสวิตช์ที่ยังไม่บันทึก
- กล่องยืนยันก่อนเผยแพร่แสดงบัญชี จำนวนคลิป และค่าที่แตกต่างรายกลุ่ม ตรวจทั้ง Desktop UIและbackend ไม่เชื่อเฉพาะปุ่ม disabled
- รองรับ1440/600/360px, labelอ่านออกด้วยตัวอ่านหน้าจอ และสั่งด้วยคีย์บอร์ดได้

**ผ่านระยะ B เมื่อ:** actual-source UI fixtureทดสอบค่าเริ่มต้น/เลือกบางงาน/ยกเลิกยืนยัน/ปิดเปิดหน้า/unsaved/บัญชีเปลี่ยน/หน้าจอเล็กครบ ไม่มี action Postจากการเปิดหน้า/เปลี่ยนสวิตช์/บันทึก defaults

### ระยะ C — ตรวจมือถือก่อนเผยแพร่และรอ animation อย่างถูกขั้น

1. เพิ่ม readerของ reuseโดยอิง resource+ข้อความกำกับจริง ไม่ทำ generic colorคลิกทุกสวิตช์ในหน้า
2. สถานะ readerเป็น `on/off/unknown` ไม่บังคับ unknownเป็นoff; ตรวจพื้นที่สวิตช์อยู่ในจอทั้งหมด ไม่ถูกทับ จับ screenshotกับXMLที่ตรงกันและนิ่งหลายตัวอย่าง
3. แยกการรอปุ่มนิ่งออกจากการคลิก: เมื่อมีanimationให้อ่านต่อโดยไม่กด หากหน้าหยุดแต่ไม่ใช่ขั้นเดิมให้พัก ไม่โยนerrorทันทีเพียงเพราะตำแหน่งเปลี่ยนหนึ่งครั้ง และไม่วนรอไม่สิ้นสุดโดยไม่มีความเปลี่ยนแปลง
4. ตั้งตาม snapshotรายคลิป เมื่อถูกแล้วไม่แตะ เมื่อกดแล้วขาดACKให้อ่านสถานะใหม่ก่อนเสมอ ไม่ blind toggleซ้ำ
5. หลังแนบสินค้าและตั้งค่าเสร็จ ตรวจแคปชัน/สินค้าตรง/reuse/AI/การแชร์ต่อครบ แล้วบันทึกหลักฐานก่อน durable Postหนึ่งครั้ง
6. อัปเดตการตรวจผลให้สัมพันธ์กับ AIที่เลือก ไม่รอป้ายเปิดในงานที่ตั้งปิด; ไม่อ้าง reuseฝั่งserverจากภาพก่อนโพสต์
7. เสริมหลักฐานผลสำเร็จไม่ให้สับสนกับโพสต์เก่า: บันทึก baselineรายการล่าสุดก่อนส่ง แล้วใช้โพสต์ใหม่/รหัสโพสต์/ลิงก์หรือหลักฐานที่อ่านได้จริงประกอบแคปชันและสินค้า ถ้ายังแยกไม่ได้ให้ unknown ไม่รับคลิปเก่าเป็นผลใหม่

**ผ่านระยะ C เมื่อ:** จำลองสวิตช์ON/OFF/ภาพว่าง/สีแปลก/บัง/ตำแหน่งเลื่อน/หลุดหลังคลิกแล้วไม่คลิกซ้ำ, preflightไม่ผ่านมีศูนย์Post, intentสูญACKยังกันซ้ำ, การตรวจผลไม่จับโพสต์เก่าที่captionเหมือนกัน

### ระยะ D — กู้การเชื่อมต่อและสถานะคิวที่เข้าใจได้

จากการอ่าน sourceเพิ่มเติม: `_refresh` ปัจจุบันเลือกตาม serial/aliasเดิม ส่วน `verified_device` probe serialที่เลือกตรง ๆ จึงยังต้องให้เลือกใหม่เมื่อ endpointเดิมไม่อยู่ กรณีมือถือเครื่องเดิมเปลี่ยนพอร์ตมีโอกาสเพิ่มความสะดวกได้ แต่ไม่ใช่เหตุผลให้ยกเลิกการตรวจตัวเครื่อง

- ตรวจ discoveryที่เข้าถึงอยู่โดยไม่ยิงpairอัตโนมัติ เมื่อพบ aliasที่เชื่อมอยู่และตรวจ hardware identityตรงเครื่องที่ผู้ใช้เคยเลือกเพียงเครื่องเดียว จึงเสนอ “พบเครื่องเดิมที่พอร์ตใหม่” หรือกู้ bindingภายใต้ device leaseตามขอบเขตที่อนุมัติ
- ชื่อรุ่น/IPเหมือนกันไม่พอ; หากหลายเครื่อง/identityไม่ตรง/ต้องจับคู่ใหม่ ให้ผู้ใช้เลือกหรืออนุญาตเอง ห้าม fallbackเครื่องแรก
- แยกเหตุผล “เครื่องเดิมหลุด/พอร์ตเปลี่ยน”, “ยังไม่อนุญาต”, “พบคนละเครื่อง”, “หน้าจอล็อก” ไม่ใช้ข้อความผิดเครื่องแทนทุกกรณี
- เชื่อมต่อกลับมาได้ไม่ได้แปลว่าส่งต่อได้ทันที: อ่านขั้น/บัญชี/ไฟล์/intentก่อน งานที่ยังไม่ส่งรอผู้ใช้กดทำต่อและตรวจหน้าเดิม; งานที่มีintentแล้วตรวจผลเดิมเท่านั้น ไม่สร้างโพสต์ใหม่
- สถานะหน้าคิวแยก **รอมือถือ / กำลังตรวจสวิตช์ / ตรวจพร้อมแล้ว / กำลังส่ง / ส่งแล้วรอตรวจ / สำเร็จ / ต้องตรวจด้วยตนเอง** พร้อมเหตุผลและปุ่มทำต่อที่เหมาะกับขั้น
- ปุ่มพักหยุดก่อนขั้นถัดไป หากกดPostแล้วไม่แสดงว่า “ยกเลิกโพสต์สำเร็จ” เพราะยังต้องตรวจผลที่ส่งไปแล้ว

**ผ่านระยะ D เมื่อ:** ทดสอบportเปลี่ยน, aliasซ้ำ, คนละเครื่อง, accountเปลี่ยน, offlineก่อน/หลังintent, pause/reopen และ unknown โดยไม่เพิ่มจำนวนPost

### ระยะ E — ตรวจรวมและเตรียมส่งมอบ

| ชั้นทดสอบ | ต้องตรวจ | การเผยแพร่ |
|---|---|---|
| Unit/fixture | options/queue/animation/switch/identity/restart/duplicate | ไม่เผยแพร่ |
| EXE-backed UI แยก instance | บันทึกค่าจริง เปิดใหม่ คิวบางแถว หน้าจอเล็ก และข้อความสถานะ | บล็อก Post |
| มือถือจริง | ค่าไปถึงหน้าก่อนโพสต์ตรงกับที่เลือก อ่านซ้ำไม่คลิกซ้ำ และกลับมาแล้วตรวจอีกครั้ง | ไม่เผยแพร่ |
| End-to-endเพิ่มเติม | ยืนยันผลใหม่และค่า AIตามงาน; คิวหลายคลิปต้องมีงบทดสอบชัดเจน | ต้องขออนุญาตใหม่ก่อน |

หลัง source settled ให้ targetedผ่านก่อน full suiteรอบสุดท้าย ตรวจ source/โฟลเดอร์/ZIPของExtension383ยังตรงกัน ไม่มี provider/model/send pathเปลี่ยน ระบุข้อจำกัดที่ยังไม่พิสูจน์แทนการบอกว่าไม่มีบั๊กแน่นอน

### แผนย้อนกลับและการส่งมอบ

- เก็บ version/schemaของoptionsและทำ migrationเฉพาะunsent; ใช้การเขียนatomicของเดิม รักษา media, transfer receipts, published/unknownและเจตนาส่งทุกครั้ง
- หากต้องย้อนเวอร์ชันระหว่างมีงานห้ามเปิดworkerเก่าให้ข้าม option preflight ใหม่โดยเงียบ; พักคิวและใช้ตัวอ่านที่รองรับschemaเดิมก่อน ห้ามคืน backupคิวเก่าทับจนลืมว่าเคยPost
- ส่งมอบ sourceพร้อมผลทดสอบ รายการไฟล์ที่เปลี่ยน และขั้นตอนเปิดโปรแกรมใหม่เมื่อไม่มีงานactive ไม่ restartผู้ใช้เอง ไม่ reload ExtensionสำหรับงานAndroidนี้
- installer/patch serverเป็นงานแยก ยังไม่รวมในระยะนี้ หากขอแพ็กภายหลังต้องทดสอบเครื่องใหม่และรวม dependencyตามแผน clean-machine เดิม

## 11. จุดหยุดก่อนลงมือ

แผนพร้อมใช้เป็นรายการลงมือ โดยเริ่ม **A → B → C → D → E** ยังไม่แก้ runtimeในรอบวางแผนนี้ และไม่มีสิทธิ์เผยแพร่โพสต์เพิ่มจากการอนุมัติวางแผนเพียงอย่างเดียว
