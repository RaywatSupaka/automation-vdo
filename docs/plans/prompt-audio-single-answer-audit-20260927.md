# แผนแก้พรอมต์ บทเสียง และการรับคำตอบเดียว

วันที่ 27 กันยายน 2026 — ตรวจซอร์สหลัก 0.15.454 แบบอ่านอย่างเดียว

## ขอบเขตและสถานะ

รวมผลตรวจสองเรื่องที่ผู้ใช้แจ้งล่าสุด: การกำกับให้ AI ตอบเพียงหนึ่งคำตอบ และบทบรรยายปนกับบทพูด/การกระทำในงานล่าสุด ไม่ใช่คำรับรองว่าตรวจทุกฟังก์ชันของโปรแกรมแล้วไม่มีบั๊ก

ใช้แนวทาง smartflow-operator และ smartflow-extension-tester แยกหลักฐานงานจริง ข้อบกพร่องในซอร์ส และสิ่งที่ยังไม่ได้ยืนยัน ไม่มีการแก้ runtime, เปลี่ยนงาน, ส่ง AI, โหลด Extension ซ้ำ, เปิดโปรแกรมใหม่ หรือบิลด์ตัวติดตั้งในรอบวิเคราะห์นี้

งานอ้างอิง: STORY-20260927-CA0334 ชื่อ “พี่ของผมเป็นฮีโร่” บันทึก Final 100 วินาทีจาก Meta 10 ฉาก โหมดเล่า narrator / เสียง flow_original / subtitle=false ใบรับผลทั้ง 10 ฉากเป็น stored

การตรวจครั้งก่อนประกอบ package ด้วยฟังก์ชันจริง โดยแทนตัวอ่านงาน/receipt ด้วยข้อมูลในหน่วยความจำ ไม่เขียนงาน พบ context_id ตรงทั้ง receipt รายฉากและ meta_clip_receipts ครบ 10/10 ฉาก จึงผูกข้อผิดพลาดของพรอมต์กับคลิปที่บันทึกได้ ไม่ใช่เพียงสมมติจากโค้ด ปัจจุบัน localhost bridge ไม่ตอบ จึงยังไม่ยืนยันเวอร์ชันที่กำลังทำงานหรือพฤติกรรมหน้าเว็บสด และยังไม่ได้ฟัง/ถอดเสียง Final

## ลำดับลงมือที่เสนอ

### 1. สร้างกรณีทดสอบที่จับบั๊กปัจจุบันได้ก่อน

ใช้ fixture สังเคราะห์ที่มีโครงเดียวกับ CA0334 และตัวอย่าง narration ที่มีคำพูดอ้างในประโยค ตรวจว่าบั๊กเกิดก่อนแก้โดยไม่เรียก AI ใช้ snapshot legacy package/receipt และไฟล์ที่บันทึกเพื่อป้องกันการเปลี่ยนงานเดิม

### 2. เพิ่มสัญญาพรอมต์แบบแยกหน้าที่สำหรับคำขอใหม่

โครงสร้างภายในควรแยกอย่างน้อย visual, motion, audio delivery, narrator text, dialogue turns และตัวเลือกเสียง/ดนตรี ไม่จำเป็นต้องให้ผู้ใช้กรอกเพิ่ม

| โหมดที่เลือก | การสร้างภาพ/การเคลื่อนไหว | เสียงที่อนุญาต |
|---|---|---|
| ผู้บรรยาย + เสียงวิดีโอ | ใช้ visual/motion ที่บันทึก | ผู้บรรยายนอกภาพอ่านบทที่กำหนด ตัวละครไม่พูดแทรก |
| ตัวละครพูด/สนทนา + เสียงวิดีโอ | การแสดงตามฉาก | เฉพาะผู้พูดและประโยคตามลำดับ ไม่มีผู้บรรยายเพิ่ม |
| พากย์แยกด้วย API | ใช้ visual/motion | ไม่สร้างคำพูดซ้ำในวิดีโอ; เก็บเสียงแวดล้อม/ดนตรีเฉพาะที่ตั้งไว้ |
| ภาพเล่าเรื่อง/ไม่มีเสียงพูด | ใช้ visual/motion | ไม่สร้างคำพูด; เสียงแวดล้อมหรือความเงียบตามค่าจริง |

นำ flow_shot_prompts จาก checkpoint มาใช้เมื่อมีข้อมูลที่ตรงจำนวนและฉาก แม้ชื่อฟิลด์มีคำว่า Flow ก็ต้องไม่ใช้เป็นเหตุผลทิ้งแผนใน Meta หากไม่มีแผนเคลื่อนไหว ห้ามใช้บทบรรยายแทน ให้สร้างข้อกำหนดเคลื่อนไหวสั้นจากข้อมูลภาพที่ยืนยันแล้ว หรือนำเข้าเส้นทางขอแผนที่มีอยู่โดยมี checkpoint ไม่ยิง AI ซ้ำจากการอ่านสถานะ

### 3. ป้องกันคำกำกับคำตอบเดียวตกหล่นก่อน Send ใหม่

รวมจุดตรวจสำหรับคำขอใหม่ทุกชนิด: บท/JSON, รูปฉาก, ปก, ซ่อมรูป, ซ่อมพรอมต์, วิดีโอ และคำตอบตกลงต่อข้อเสนอ

- ข้อความกำกับมีครั้งเดียว ไม่เพิ่มซ้ำ และไม่เปลี่ยนจำนวนฉาก/schema/บทพูด/เสียง
- หาก helper ยังไม่พร้อม ให้แก้ขั้นเตรียมก่อน Send ไม่ปล่อยส่ง raw เพราะ optional fallback
- ร่างเดิมเปลี่ยนได้เฉพาะพิสูจน์ว่าเป็นร่างของคำขอที่ยังไม่ส่ง ไม่แตะร่างผู้ใช้
- คำขอที่ส่งไปแล้ว/ไม่ทราบผลต้องอ่านผลเดิมก่อน ไม่ replay เพื่อเติม suffix
- Native Retry ของคำขอเก่าไม่ถือว่าได้เติมคำกำกับใหม่แล้ว หากต้องสร้างคำขอใหม่ ใช้ successor ที่บันทึกก่อนส่ง

### 4. ปิดทางค้างเมื่อ AI ยังแสดงหลายคำตอบ

คำสั่ง “คำตอบเดียว” เป็นข้อกำกับ ไม่ใช่การควบคุมหน้าเว็บของผู้ให้บริการ จึงต้องมีตัวรับผลรองรับ

- รอให้ผลของคำขอนั้นพร้อมจริง ไม่กด Stop ระหว่างสร้าง
- รูปหลายใบ: เลือกผลที่โหลดสำเร็จหนึ่งใบของฉากนั้น บันทึก asset ที่เลือกให้คงที่ และไม่หยิบรูปอ้างอิง/ฉากก่อนหน้ามาแทน
- วิดีโอหลายชิ้น: เลือกวิดีโอที่เล่นได้หนึ่งชิ้นของคำขอเดิม ไม่เลือกจากคำกล่าวว่า “สร้างเสร็จ” และไม่กดโหวตความชอบ
- JSON หลายตัวเลือก: ตรวจทีละตัวเลือก เลือกชุดเดียวที่ตรง schema และมีฉากครบ ห้ามนำสองคำตอบมาต่อกัน
- Meta เสนอหลายแนวทางแต่ไม่มีวิดีโอ: เลือกข้อเสนอที่รองรับหนึ่งข้ออย่างชัดเจนหรือเข้าสู่เส้นทางแก้ที่มีอยู่ ไม่ตอบตกลงรวมและไม่รอผลที่ไม่มีวันเริ่มสร้าง
- หากผลเสร็จแล้วแต่ใช้ไม่ได้: บันทึกเหตุผลเฉพาะชนิด แล้วเข้าสู่วงรอบซ่อมที่มีเจ้าของคำขอและช่วงพัก ไม่เริ่มคำขอใหม่ทุกครั้งที่ตรวจสถานะ
- Login/เครดิต/บริการไม่รองรับ/การปฏิเสธจริง แยกจาก technical error และแสดงสิ่งที่ต้องจัดการ ไม่กล่าวอ้างว่าจะวนจนสำเร็จได้ทุกกรณี

### 5. รักษางานเก่าและการทำต่อ

hash ของ Meta ผูกกับพรอมต์ทั้งข้อความ ดังนั้นเปลี่ยน builder เดิมโดยตรงจะทำให้ receipt เก่าไม่ตรง ต้องกำหนดเวอร์ชันสัญญาใหม่สำหรับงาน/คำขอใหม่ และคง bytes ของ legacy ที่ส่งแล้วไว้

Flow motion plan ก็รวม audio_instruction ใน context hash เช่นกัน จึงต้องมีเงื่อนไขรุ่นเมื่อแก้ helper เสียงร่วม ไม่เปลี่ยนข้อความทุกงานย้อนหลัง

- CA0334 มีคลิปครบแล้ว ห้ามสร้างใหม่หรือเปลี่ยน Final อัตโนมัติ
- งานกำลังทำหรือรอผล ใช้ receipt เดิมจนขั้นนั้นสิ้นสุด
- หากผู้ใช้สั่งแก้ฉากเก่า ให้เก็บ attempt เดิมและสร้าง successor เฉพาะฉาก โดยเก็บสื่อสำเร็จอื่นไว้
- การเปลี่ยนฟังก์ชันเสียงร่วมต้องไม่ทำให้ Flow หรือ Meta helper override เก่าเปลี่ยน context โดยไม่ได้รับอนุญาต

### 6. ทดสอบและส่งมอบ

ทดสอบแบบไม่เสียเครดิตก่อน: Shorts/Product/Drama/Long; narrator/solo/dialogue/visual; API/native/silent; ดนตรีเปิด/ปิด; แนวตั้ง/แนวนอน; งานใหม่/งานเก่า/กดทำต่อ

เกณฑ์สำคัญ:

1. บทบรรยายไม่อยู่ใน Action; visual directions ไม่อยู่ในช่องคำพูด
2. narrator ไม่มีบทตัวละครแทรก; dialogue ไม่มีผู้บรรยายที่ไม่ได้สั่ง
3. จำนวนฉากและคำพูดที่เลือกคงเดิม ไม่บีบทุกอย่างเหลือฉากเดียวเพราะคำว่า “หนึ่งคำตอบ”
4. ทุก new-send มีคำกำกับหนึ่งครั้ง; helper หาย/ร่างเก่า/Retry ไม่หลุดออกทาง raw โดยไม่ทราบ
5. หลายภาพ/วิดีโอ/JSON เลือกได้หนึ่งผลที่ตรงคำขอ; ไม่ใช้ของเก่า ไม่เปลี่ยนตัวเลือกไปมา
6. งานกำลังสร้าง: ไม่มี Send/Stop ซ้ำ; แจ้งความคืบหน้าอย่างตรงสถานะ
7. Refresh/restart/ACK หาย: ไม่มี successor ซ้อน ไม่มีการบันทึกผลซ้ำ
8. package hash, รูป/คลิปและ Final ของงานสำเร็จเดิมไม่เปลี่ยน

ชุดทดสอบเดิมที่ต้องขยาย: test_meta_video.py, test_media_audio_choices.py, test_story_performance.py, test_storytelling_397.py, test_single_answer_412.py, test_motion_transport_414.py, meta_comparison_412.cjs และ receipt/cover/recovery harness ที่เกี่ยวข้อง หลังแก้ครบค่อยรันทดสอบรวมหนึ่งรอบ

ทดสอบผู้ให้บริการจริงเป็นขั้นแยกหลังผู้ใช้ยืนยันขอบเขตและเครดิต ตรวจเทียบคำสั่งที่ส่งกับภาพ/เสียงที่ได้จริง ไม่ถือว่าทดสอบออฟไลน์ผ่านเท่ากับ Meta ทำเสียงถูกแล้ว

ส่งมอบซอร์สหลักและ Extension ที่เข้ากัน พร้อมรายงานทดสอบและไฟล์ Extension ใน deliverables เมื่อถึงขั้นเตรียมรุ่นใหม่ ไม่รีโหลดงานสดเอง และยังไม่บิลด์ตัวติดตั้งจนผู้ใช้สั่ง

บั๊กที่ผูกกับงานจริงอยู่ฝั่งประกอบพรอมต์ของโปรแกรม ส่วน Extension มีหน้าที่บังคับสัญญาการส่งและรับผลให้ไม่ค้าง ทั้งสองฝั่งต้องทดสอบร่วมกัน แต่ไม่จำเป็นต้องรื้อทุกระบบหรือสร้างคลิปที่สำเร็จแล้วใหม่
