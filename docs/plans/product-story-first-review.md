# แผน: เล่าเรื่องก่อน รีวิวแบบเป็นธรรมชาติ — Shopee Product

วันที่: 2026-09-21
สถานะ: วิเคราะห์จาก source 0.15.393 และเสนอแผนเท่านั้น ยังไม่ลงมือแก้ runtime

อัปเดต 2026-09-21: ผู้ใช้อนุมัติและลงมือเป็น 0.15.394 แล้ว ดูผลจริงและสิ่งที่ยังไม่ทดสอบใน `docs/reports/product-story-first-394.md` เนื้อหาด้านล่างเก็บเป็นแผนต้นฉบับ ไม่ใช่สถานะ runtime ล่าสุด

## เป้าหมาย

เพิ่มตัวเลือกก่อนเริ่มสร้างคลิปสินค้า ให้ AI เขียนบทเหมือนตัวละครผู้รีวิวมีมุมมองและบุคลิกของตัวเอง เปิดด้วยเหตุการณ์ชวนติดตาม แล้วค่อยเชื่อมเข้าสินค้าอย่างสมเหตุสมผล ไม่เปิดด้วยชื่อสินค้ายาว/ราคา/รายการสเปก และไม่ยัดปิดการขาย

ใช้ได้กับ ChatGPT Web และ Gemini Web ที่ผู้ใช้เลือก ไม่เพิ่มรอบถาม AI เพื่อเขียนบทแยกอีกครั้งเป็นค่าเริ่มต้น

## สิ่งที่ตรวจพบจริง

- `web_ui/product_story.js` เตรียมข้อมูลสินค้า/ตัวละคร แล้วส่ง `creative_context.kind=product_story` พร้อม `story_text` และจำนวนฉาก ทั้งสร้างทันทีและเข้าคิว หน้า Shopee รุ่นปัจจุบันจึงใช้ Story pipeline ไม่ใช่ Product legacy ทุกกรณี
- `ui/main_window.py::_desktop_execute_action` และ `ui/creation_queue.py::_creation_queue_action` เปลี่ยนคำสั่งดังกล่าวไปเส้นทาง Story; งานเดิมยังมีเส้นทางเดิมของตัวเอง
- `core/product_story.py::story_brief` ขอ hook → เหตุการณ์ → ใช้งานสินค้า → บทสรุปอยู่แล้ว แต่ยังเป็นคำสั่งกว้าง ไม่มีตัวเลือกแยกโหมด story-first และไม่มีข้อกำหนดบุคลิก/น้ำเสียงผู้เล่าละเอียด
- คำสั่งให้ผู้รีวิวที่เห็นในภาพพูดตรงกับกล้องใช้เฉพาะ `product_native_delivery`: product presentation v1 และเสียงต้นคลิป `flow_original` ไม่ได้ใช้ทุกโหมดเสียง
- `core/story_manager.py::_write_request` ยังมีแม่แบบผู้บรรยายและข้อบังคับชวนกดหัวใจ/คอมเมนต์ ก่อนต่อ product brief มีการเติม CTA ภายหลังด้วย `_ensure_engagement_cta` ในรับผล/แก้บท/กู้ checkpoint บางเส้นทาง ดังนั้นแก้ prompt อย่างเดียวอาจถูกเติมประโยคท้ายกลับมา
- `core/product_manager.py::_write_ai_request` สำหรับ Product legacy เน้นเปิดสินค้า → รายละเอียด → ภาพไลฟ์สไตล์ปิดการขาย และน้ำเสียงผู้รีวิวมืออาชีพ เป็นอีกเส้นทางหนึ่ง ห้ามแก้รวมจนเปลี่ยนงานเก่า
- `browser_extension/chatgpt.js` รับ `pkg.prompt` จากโปรแกรม แล้วเสริมกติกา JSON/จำนวนฉาก/การส่งครั้งเดียวก่อน `submitPrompt` ตัวบทหลักจึงควรออกแบบที่โปรแกรม ไม่ทำแม่แบบแยกซ้ำในแต่ละเว็บ
- ตัวช่วยเติม JSON ที่ไม่ครบมีคำสั่งคงข้อมูลเดิม แต่ต้องตรวจให้ตัวเลือกใหม่นี้ติดไปในคำขอซ่อมด้วย ไม่ให้ฉากที่เติมกลับเป็นสไตล์ขายตรง

ข้อสรุปนี้เป็นหลักฐานจากโค้ด ไม่ใช่ผลประเมินบทหรือคลิปที่เพิ่งสร้างจริง รอบนี้ไม่ส่งข้อความไป AI ไม่สร้างภาพ/คลิป และไม่ขัดจังหวะ Story ที่กำลังทำงาน

## UX/UI ที่เสนอ

วาง checkbox เดียวในส่วนวางแผนคลิปสินค้าก่อนปุ่มสร้าง/นำเข้าคิว:

**เล่าเรื่องก่อน รีวิวแบบเป็นธรรมชาติ**

ข้อความช่วย: “เปิดด้วยเหตุการณ์น่าสนใจ ให้ตัวละครเล่า แล้วค่อยเชื่อมเข้าสินค้า ไม่เน้นขายตรง”

- ปิดไว้สำหรับผู้ใช้เดิมเพื่อรักษาพฤติกรรมเดิม จำค่าครั้งล่าสุดสำหรับงานใหม่
- ใช้ช่องแนวเรื่อง/รายละเอียดเดิม `ps-details` ไม่เพิ่มฟอร์มหรือหน้าตั้งค่าซ้ำ แสดงตัวอย่างแนวเรื่องสั้นเมื่อเปิด
- การสร้างทันทีและนำเข้าหลายลิงก์ใช้ค่าเดียวกันที่บันทึกตอนกด ก่อนรอนำเข้าข้อมูล ไม่อ่านค่าใหม่กลาง batch
- แสดงชื่อแนวบทสั้น ๆ ในสรุปตั้งค่างานเดิมที่มีอยู่ ไม่เพิ่มการ์ดหรือคิวใหม่
- ไม่เปิดโหมดตัวละครสนทนา ไม่เปลี่ยนเสียง/คำบรรยาย/ตัวละคร/ผู้ให้บริการ/จำนวนฉากให้เอง

## กติกาบทสำหรับโหมดใหม่

1. เปิดด้วยความตั้งใจ ปัญหาเล็ก ๆ หรือเหตุการณ์ในชีวิตประจำวันหนึ่งเรื่อง มีเหตุให้ดูต่อในประโยคแรก ไม่เริ่มว่า “วันนี้จะมารีวิว…” เป็นสูตรทุกคลิป และไม่อ่านชื่อสินค้ายาว
2. ผู้เล่ามีบุคลิกและสรรพนามคงที่ ใช้ประโยคพูดจริงสั้น ๆ มีจังหวะคิด/ปฏิกิริยา ไม่ใช่ผู้บรรยายอ่านคุณสมบัติให้ตัวละครขยับปาก
3. เชื่อมสินค้าเข้ากับเหตุการณ์โดยมีเหตุผล ใช้ข้อมูลจริงที่เกี่ยวข้องหนึ่งถึงสองประเด็น ไม่ไล่สเปกทั้งหมด ไม่ต้องย้ำชื่อสินค้าทุกฉาก
4. ฉากแรกเน้นเหตุการณ์ได้ สินค้าอาจอยู่ในภาพอย่างเป็นธรรมชาติ แต่ไม่บังคับโชว์เด่นทุกฉาก คงรูปร่าง/สี/อัตลักษณ์ตามแหล่งอ้างอิง
5. จบเหตุการณ์ให้ครบ ไม่บังคับ “ซื้อเลย/ต้องมี/ลิงก์ด้านล่าง” หรือชวนกดหัวใจ/คอมเมนต์ทุกคลิป อนุญาตคำถามที่เข้ากับเรื่องเมื่อเหมาะสม แต่ไม่เติมอัตโนมัติ
6. แต่งสถานการณ์และบุคลิกได้ แต่ไม่แต่งประวัติการใช้จริง การซื้อจริง ผลทดลอง คำรับรอง สเปก ราคา หรือสรรพคุณ โดยเฉพาะผลสุขภาพ “เหมือนมีตัวตน” หมายถึงการเขียนตัวละคร ไม่ใช่ปลอมหลักฐานประสบการณ์สินค้า
7. ให้จำนวนฉากและความยาวบทพอดีระยะเวลาที่เลือก สามฉากย่อเป็นเปิดเหตุการณ์ → ใช้สินค้า → บทสรุป; หกถึงสิบห้าฉากขยายเหตุการณ์ที่จำเป็น ไม่ยืดเปิดเรื่องหรือพูดซ้ำเพื่อครบจำนวน
8. สร้าง `scene_narrations`, `scene_dialogue_turns`, `scene_prompts` และแผนการเคลื่อนไหวจากเรื่องเดียวกัน บทพูดรายฉากต้องตรงกัน ไม่ให้ Flow แต่งบทใหม่เองภายหลัง

เสียงต้นคลิป: ผู้รีวิวในภาพพูดเองตามบท มีท่าทางและปฏิกิริยาที่เข้ากับเรื่อง รักษาตัวละครเดิม

เสียง API: ใช้บทเล่าบุคคลที่หนึ่งแบบเดียวกันเป็นเสียงเล่า ไม่สัญญาว่าปากตัวละครจะตรงเสียง และไม่เพิ่มการพูดในวิดีโอชนกับเสียง API โดยอัตโนมัติ

ตัวอย่างโทนที่ต้องการ (สมมติสินค้าเป็นโคมไฟตั้งโต๊ะ ไม่ใช่ผลจาก AI): “ว่าจะอ่านอีกแค่หน้าเดียว… รู้ตัวอีกทีบ้านเงียบหมดแล้ว” → หยิบโคมไฟเข้ามาเกี่ยวกับกิจกรรม → กล่าวถึงรายละเอียดที่ยืนยันได้ → จบด้วยเหตุการณ์เดิม ไม่ตัดไปอ่านโฆษณา

## สัญญาข้อมูลและขอบเขตแก้

เสนอ `product_script_options: {version: 1, style: "standard" | "story_first_review"}` ตรวจค่าแบบชัดเจน บันทึกใน snapshot ของคิวและ Job ก่อนเขียนคำขอ AI พร้อมใส่ metadata ใน request

- ไม่มี field = legacy behavior ห้ามย้ายงานเก่ามาโหมดใหม่โดยเงียบ ๆ
- หน้าสร้างใหม่รับจาก payload; งานคิว/Resume รับจากค่าของงานเท่านั้น ไม่อ่านฟอร์มปัจจุบันทับ
- เพิ่ม whitelist/copy/validation/fingerprint ให้ครบใน `core/creation_queue.py` และ `ui/creation_queue.py`; ส่งต่อในการสร้างงานที่ `ui/main_window.py` ไป `core/story_manager.py`
- สร้างตัว normalize และ brief กลางเล็ก ๆ สำหรับโหมดนี้ ใช้ร่วมกับ `core/product_story.py` ไม่สร้าง scheduler หรือระบบ prompt อีกชุด
- จัดองค์ประกอบแม่แบบ Story แบบมีเงื่อนไขสำหรับ product style นี้: เปลี่ยนกติกาผู้เล่า/ตอนจบที่ขัดกัน ไม่ต่อคำสั่งใหม่ทับแม่แบบเดิมแล้วปล่อยให้ AI เลือกเอง ไม่ใช้การค้นแทนข้อความกว้าง ๆ กับ prompt ที่ผู้ใช้เขียน
- มีเงื่อนไขกลางเดียวควบคุมการเติม CTA สำหรับโหมดใหม่ ครอบรับผล แก้บท และกู้ checkpoint ป้องกันเสียงท้ายคลิปหลุดโทน
- Extension ใช้ brief เดิมที่บันทึกแล้วสำหรับทั้ง ChatGPT/Gemini ตรวจเส้นทางซ่อม JSON/เติมฉากและตัวช่วยภาพ/Flow ให้คง style + ข้อเท็จจริง + บทที่อนุมัติ ห้ามซ่อมภาพแล้วเขียนคำพูดขายใหม่
- ไม่เปลี่ยนตัวอ่านผลล่าสุด, Scroll/reveal, Send, upload, receipt, retry controller, login หรือการผูก job/run/tab ของ Extension ในงานนี้ หากต้องแก้ metadata/repair prompt ให้จำกัดเฉพาะส่วนนั้น
- Product legacy ที่ไม่มีตัวเลือกนี้คง prompt เดิม ส่วนฟีเจอร์ใหม่เปิดเฉพาะเส้นทางหน้า Shopee ปัจจุบัน ไม่ไปเปลี่ยน Story ทั่วไป/ละคร/ตัวละครสนทนา

## ลำดับลงมือและการตรวจรับ

1. เพิ่มสัญญาข้อมูลและ test snapshot ก่อน: สร้างทันที/เข้าคิว/เริ่มคิว/เปิดใหม่/ทำต่อยังได้ค่าเดิม รวมการเปลี่ยน checkbox ระหว่างรอนำเข้าหลายลิงก์
2. เพิ่ม checkbox และคำอธิบายในฟอร์มเดิม ตรวจค่าเริ่มต้น/ค่าที่จำไว้/ปิดแล้วกลับสไตล์เดิม โดยไม่เพิ่มขั้นกดก่อนเริ่ม
3. ปรับแม่แบบและเงื่อนไข CTA ร่วมกัน ทดสอบ ChatGPT/Gemini, สาม/หก/สิบห้าฉาก, เสียง API/ต้นคลิป, เลือก/ไม่เลือกตัวละคร และการรักษาข้อมูลสินค้า
4. ตรวจ Extension ซ่อม JSON/Resume/ซ่อมภาพ-พรอมต์ให้ไม่ทิ้งโหมดหรือเปลี่ยนบทเดิม; เพิ่ม fixture จาก source จริง ไม่ทดสอบแค่ข้อความจำลอง แยกทดสอบความถูกต้องของรูปแบบกับคุณภาพการเขียน
5. ตรวจเชิงคุณภาพ: hook เป็นเหตุการณ์จริงในเรื่อง, ผู้เล่ามีมุมมองคงที่, สินค้าเข้ามาอย่างมีเหตุผล, บทพูดสั้นพอดีเวลา, ไม่มีประสบการณ์ปลอมหรือคำขายซ้ำ ไม่ใช้ regex ตัดสินว่า “ไม่เป็นธรรมชาติ” แล้วสั่งวนซ่อมไม่สิ้นสุด
6. หลังผู้ใช้อนุมัติลงมือและเมื่อไม่มีงานอื่นถูกขัดจังหวะ จึงทดสอบเว็บจริงแบบขอบเขตชัดเจน: เปรียบเทียบบทเก่า/ใหม่จากสินค้าข้อมูลเดียวกันก่อน แล้วสร้างคลิปตัวอย่างหนึ่งงานเมื่อได้รับขอบเขตทดสอบ ไม่โพสต์ Shopee จริงในงานนี้
7. หากแก้ Extension runtime ให้จับคู่รุ่น/แพ็กเกจตามสัญญาปัจจุบันพร้อม regression tests แต่ไม่ reload ขณะมีงานทำอยู่ และแยกผล offline tests ออกจาก installed E2E ตามจริง

## นอกขอบเขตรอบวางแผน

ยังไม่แก้โค้ด ไม่เพิ่มเลขรุ่น ไม่เปลี่ยนคิว/งาน/บทที่บันทึกแล้ว ไม่เปิดหน้า AI ส่งงาน ไม่รีโหลดโปรแกรมหรือ Extension และไม่แก้เซิร์ฟเวอร์
