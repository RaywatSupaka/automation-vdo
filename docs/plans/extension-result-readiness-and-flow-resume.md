# แผนแก้ Extension: อ่านคำตอบให้ครบ และทำต่อเมื่อ Flow พร้อม

วันที่: 2026-09-20

สถานะ: **แก้ source และแพ็ก 0.15.392 เสร็จแล้ว — ตรวจ full suite และแก้ fixture เดิมหนึ่งจุด; ตรวจซ้ำ 202 รายการผ่าน / ยังไม่ติดตั้งหรือรีโหลด Chrome** ดูผลที่ [รายงาน 392](../reports/result-readiness-392.md)

ฐานปัจจุบัน: 0.15.391 คู่โปรแกรมเดียวกัน รุ่นส่งมอบถัดไปคาดว่า 0.15.392 แต่ต้องตรวจเลขล่าสุดก่อนเริ่ม ไม่ใช้เลขซ้ำกับโค้ดคนละชุด

## เป้าหมายและหลักฐาน

1. ผู้ใช้ไม่ต้องเลื่อน ChatGPT ลงสุดเองเพื่อให้ Extension รับคำตอบ/รูปของงานปัจจุบัน
2. Flow ที่มีภาพ พรอมต์ และค่าครบ ต้องไปต่อได้ แม้เว็บจัดย่อหน้าต่างจากข้อความต้นฉบับ
3. งานที่ส่งแล้วหรือไม่ทราบผลการส่งต้องไม่ถูกส่งซ้ำ และต้องแสดงสาเหตุจริงเมื่อไปต่อไม่ได้

หลักฐานอ้างอิง:

- [ChatGPT: รูปโหลดครบแต่ขนาดบนหน้าเป็นศูนย์](../reports/chatgpt-scroll-391/README.md): ยืนยันด้วย source + fixture; กลไก lazy rendering ในแท็บจริงยังไม่ได้ยืนยัน
- [Flow: A72FDE ฉาก 4](../reports/chatgpt-scroll-391/flow-A72FDE.md): ยืนยันจาก log และ DOM จริง พรอมต์ 756 ตัวกลายเป็น 757 ตัวเพราะบรรทัดว่างเพิ่ม แต่ข้อความไม่เปลี่ยน ปุ่ม Generate เปิดใช้งานและเลือกโหมด 0 เครดิต
- มี diagnostic fixtures อยู่แล้ว ต้องเปลี่ยนเป็น regression ของพฤติกรรมที่ถูกต้องเมื่อเริ่มแก้ ไม่ถือว่าการทดสอบยืนยันบั๊กผ่านเท่ากับแก้บั๊กผ่าน

## ขอบเขตที่ไม่เปลี่ยน

- ไม่เพิ่มระบบตรวจ API Token กลับเข้า Extension; Desktop Login ยังคงเดิม
- ไม่เปลี่ยนผู้ให้บริการ โมเดล สัดส่วน ความยาว เสียง หรือจำนวนผลลัพธ์ที่ผู้ใช้เลือก
- ไม่ปรับลอจิก Gemini/Meta หรือยกเครื่อง Send/attachment ทั้งระบบ
- ไม่ล้าง queue, checkpoint, receipt, ภาพหรือคลิปเดิม ไม่เปิดโปรเจกต์ใหม่เพื่อแก้ปัญหาการอ่าน DOM
- ไม่เพิ่มการวนสร้างใหม่ เปลี่ยนพรอมต์เพื่อเลี่ยง policy หรือใช้ภาพนิ่งแทนวิดีโอ
- ไม่แก้เซิร์ฟเวอร์ ไม่ทำ installer และไม่รีโหลด Extension ขณะมีงานหรือผลการส่งที่ยังไม่แน่ชัด

## ลำดับลงมือ

### P0 — เก็บ baseline และสร้าง regression ก่อนแก้

- ตรวจ manifest / desktop required version / installed evidence ให้ตรงกัน และตรวจว่างานจริงว่าง
- เก็บ fingerprint เฉพาะไฟล์ที่จะเปลี่ยน ไม่แตะ cumulative user changes
- นำ fixture ย่อหน้า Flow และภาพ ChatGPT ที่ขนาดหน้าจอเป็นศูนย์มาทดสอบ expected behavior ใหม่ ให้เห็นว่ารุ่นเดิมไม่ผ่าน
- แยกผลตรวจเป็น source fixture, installed read-only และ real generation ไม่รวมเป็นคำว่า “ผ่านทั้งหมด”

### P1 — แก้ Flow ก่อน: เปรียบเทียบพรอมต์และเดินต่อจาก prepared

ไฟล์หลัก: `browser_extension/flow.js`, `browser_extension/background.js`

1. ทำกติกาเปรียบเทียบ **ข้อความครบทั้งพรอมต์** ให้ตรงกันทุกจุด: initial readiness, fresh-project re-entry, prepress และการตรวจคำขอเดิมในประวัติ
2. รองรับ CRLF/LF, บรรทัดว่างจาก `<p>` และช่องว่างที่เว็บใช้แสดงผล โดยยุบเป็นตัวคั่นมาตรฐาน ไม่ตัดคำ เครื่องหมาย ตัวเลข หรือบทพูดภาษาไทย และไม่เทียบเพียง 24 ตัวแรก
3. ไม่แก้ canonical prompt หรือ hash/identity ของ receipt เดิมเพื่อทำให้ผลเทียบผ่าน การปรับรูปแบบใช้เฉพาะตรวจ DOM กับข้อความที่คาดไว้
4. ถ้า job/run/repair/project, ภาพของรอบนี้, พรอมต์เต็ม และค่าที่ผู้ใช้เลือกตรงกัน ให้เดินต่อผ่านธุรกรรมกดสร้างเดิมหนึ่งครั้ง ไม่ upload/refill/open project ซ้ำ
5. หากมี receipt การส่งอยู่แล้ว ให้เข้าโหมดติดตามผลเดิม ไม่เข้าสาขากดใหม่
6. ตรวจ queued preparation ที่กลับเข้าซ้ำ: รวมคำขอซ้ำของเจ้าของงานเดียวกันและตรวจสถานะใหม่หลังทุก `await` ไม่ให้ stale callback ทำให้สถานะถอยหลังหรือกดซ้ำ ทั้งนี้ยังไม่ฟันธงว่าเหตุการณ์ล่าสุดมี worker ทำงานพร้อมกัน
7. ตรวจ history/composer duplicate guard ด้วยข้อความหลายย่อหน้า ไม่ให้การแก้ normalization ทำให้ตรวจโพสต์เดิมไม่เจอ

เกณฑ์ผ่าน P1: fixture แบบภาพเหตุการณ์เดิมต้องพร้อมกดครั้งเดียว; ข้อความที่แก้ท้ายพรอมต์/บทพูดหรือถูกตัดต้องไม่ผ่าน; receipt เดิมต้องทำให้จำนวนคลิกใหม่เป็นศูนย์

### P2 — แก้ ChatGPT: อ่านผลโดยไม่ผูกกับตำแหน่งหน้าจอ

ไฟล์หลัก: `browser_extension/chatgpt.js`

1. แยกการอ่านผลออกจาก helper `visible()` ที่ใช้กับปุ่มกด ไม่แก้ visibility ทั้งระบบ
2. เฉพาะคำตอบที่ผูกกับคำขอ/ฉากปัจจุบัน: ใช้ขนาดจริงของภาพที่ decode แล้ว แม้ layout ถูกยุบ คงเงื่อนไข URL ผู้ให้บริการ ขนาดขั้นต่ำของแต่ละเส้นทาง และความคงที่ก่อนบันทึก
3. ใช้การตัดภาพต้นทาง ภาพเก่า ภาพไอคอน และการรวมหลายชั้นของรูปเดียวกันแบบเดียวกันทั้ง baseline และผลลัพธ์ ไม่ขยายการยอมรับเฉพาะฝั่งผลจนภาพเก่าถูกนับเป็นภาพใหม่
4. ถ้าข้อความยังอยู่ใน DOM ให้อ่านได้ทันทีโดยไม่เลื่อน ถ้า node ยังไม่ mount หรือรูปต้อง lazy-load จึงเปิดดูคำตอบในพื้นที่เลื่อนของบทสนทนาที่ถูกต้อง ไม่เลื่อน sidebar/คลังภาพ/แท็บอื่น
5. จำกัดการ reveal เป็นรอบสั้นแบบยกเลิกได้ เช่น สูงสุด 3 ครั้งต่อสภาพ DOM ที่ไม่เปลี่ยน และเว้นช่วง ไม่เลื่อนทุก poll ไม่แย่งการเลื่อนของผู้ใช้อย่างต่อเนื่อง ตัวเลขนี้เป็นค่าเริ่มต้นที่จะตรวจด้วย fixture ไม่ใช่ timeout ให้สร้างใหม่
6. หลัง reveal ให้ค้น node และตรวจเจ้าของใหม่ ห้ามเก็บ reference ของ DOM เก่าแล้วถือว่าเป็นคำตอบปัจจุบัน หยุดการ reveal ถ้า run/conversation เปลี่ยนหรือผู้ใช้ยกเลิก
7. ใช้ร่วมกับการรอ text/image ครั้งแรกและ Resume; Product ต้องมี ownership ที่เพียงพอก่อนใช้ relaxed geometry ไม่เปิดรับภาพจากทั้งหน้า
8. ถ้ายังไม่พบผล ให้แจ้งกำลังอ่านคำตอบ/โหลดรูปอย่างถูกต้อง และคง no-resend หาก provider ยังทำงานให้รอต่อ การไม่พบ DOM ไม่ใช่หลักฐานว่างานไม่เคยส่ง

เกณฑ์ผ่าน P2: ผลของงานเดิมที่พร้อมแล้วถูกอ่านได้ทั้งด้านบน/ล่าง/ยุบ layout/ถอดแล้ว mount ใหม่ โดยไม่มี Send, Stop, Refresh, reupload หรือแท็บใหม่จาก recovery นี้

### P3 — แสดงสาเหตุและแหล่งที่มาของข้อผิดพลาดให้ตรง

ไฟล์หลัก: `flow.js`, `background.js`; ตรวจเส้นทาง `core/local_bridge.py` และ popup/error formatter ของ desktop เฉพาะจุดที่ต้องส่งข้อมูลต้นทาง

- แยก “ตรวจไม่ผ่านก่อนส่ง” ออกจาก “ข้อผิดพลาดหลังส่ง” ไม่ให้ handoff filter กลืน pre-submit error ที่เป็นของงานปัจจุบัน
- ยืนยัน tab/run/repair/project ทุกครั้ง; ห้ามเปิดรับ error จากรอบเก่าหรือให้ pre-submit error ย้อนทับงานที่ submitted แล้ว
- Log เก็บเหตุผลย่อย เช่น prompt mismatch / image not ready / settings mismatch / waiting for button พร้อมความยาวและ fingerprint แบบไม่เก็บพรอมต์เต็มหรือข้อมูลลับ
- หน้า error แสดงต้นเหตุและ URL ของ Flow แม้ ChatGPT/Story เป็นผู้รายงานต่อ พร้อมเก็บ outer context แยกกัน
- สถานะระหว่างทำงานใช้ข้อความตรงเหตุการณ์: “กำลังเปิดดูคำตอบล่าสุด”, “ตรวจรูปและพรอมต์ครบแล้ว”, “ส่งคำขอสร้างแล้ว”, “รอผลจาก Flow” โดยต้องมีหลักฐานก่อนขึ้นสถานะส่งแล้ว

## ชุดทดสอบก่อนแพ็ก

| ส่วน | กรณีที่ต้องครอบคลุม |
|---|---|
| Flow ข้อความ | หนึ่ง/หลายย่อหน้า, CRLF, บรรทัดว่าง, ภาษาไทย, เปลี่ยนบทพูด/ท้ายข้อความจริง, ข้อความถูกตัด |
| Flow การทำต่อ | prepared เดิม, callback ซ้ำ, receipt มีแล้ว, ไม่ทราบผลการส่ง, run/project/ภาพผิด, cancel ระหว่างรอ |
| ChatGPT ข้อความ | offscreen แต่ยังอยู่ใน DOM, zero-size, mount ใหม่, response ยังเปลี่ยน, owner หาย/ผิด |
| ChatGPT ภาพ | decoded แต่ layout ยุบ, lazy loading, roleless answer, หลายชั้นรูปเดียว, ภาพให้เลือกสองใบ, ภาพเก่า/ภาพอ้างอิงกลับมา |
| การเลื่อน | nested scroller, sidebar ยาว, บทสนทนาสั้น, ผู้ใช้เลื่อนเอง, เปลี่ยนแท็บ/งานขณะรอ, ขอบเขตจำนวน reveal |
| ความเข้ากันได้ | Gemini/Meta/cover เดิม, Flow settings, ไม่มี Extension membership gate กลับมา |
| Error | pre-submit ของงานปัจจุบันผ่านถึง desktop, stale/foreign event ถูกปฏิเสธ, ไม่ทับ submitted state |

เริ่มจาก harness ของอาการและชุดเดิม `ai_analysis_completion_harness.js`, `story_image_scope_328_harness.js`, `story_image_wait_342_harness.js`, `flow_handoff_365.js`, `flow_fresh_project_harness.js`, `test_flow_settings.py`, `test_flow_video_settings.py` พร้อม bridge/receipt/no-membership regressions ที่เกี่ยวข้อง

เมื่อโค้ดนิ่ง: รัน full suite หนึ่งรอบ ตรวจ syntax/version และ source↔folder↔ZIP parity บันทึกผลจริงและปิดเฉพาะทรัพยากรทดสอบของเรา

## อัปเดตและทดสอบของจริง

1. เพิ่มเลข Extension/desktop required/helper build/release metadata พร้อมกัน เก็บแพ็กเดิมไม่เขียนทับ
2. อัปเดตผ่านโฟลเดอร์ถาวร `browser_extension` และ Chrome profile/Extension identity เดิม ไม่ถอนแล้วติดตั้งใหม่ ไม่ล้าง storage
3. ติดตั้ง/รีโหลดเฉพาะเมื่อผู้ใช้สั่งและตรวจว่าไม่มีงานหรือผลการส่งค้าง ต้องตรวจ installed version และ connection จริงหลังอัปเดต
4. ทดสอบอ่านคำตอบ/รูปที่สร้างไว้แล้วก่อน ไม่ขอ AI สร้างใหม่เพื่อทดสอบการอ่าน
5. หากได้รับอนุญาตให้ทดสอบสร้างจริง ให้จำกัดหนึ่งฉาก เริ่มจาก A72FDE ฉาก 4 เฉพาะเมื่อยังตรวจได้ว่าเป็น prepared ที่ไม่เคยส่ง ใช้ภาพ/พรอมต์ที่บันทึกไว้และค่าที่ผู้ใช้เลือก ตรวจราคาใหม่ก่อนกด ห้ามถือว่า 0 เครดิตเดิมจะคงอยู่ตลอด
6. หากผลการส่งไม่ชัดเจน ให้ตรวจ receipt/ผลเดิม ไม่ลอง Generate ซ้ำเพื่อให้เทสผ่าน เก็บฉาก 1–3 และ replacement ฉาก 4 ไว้ครบ

## สิ่งที่จะส่งมอบเมื่อทำจริง

- Extension รุ่นใหม่พร้อม desktop ที่จับคู่ถูกต้อง และไฟล์ ZIP ของรุ่นนั้น
- Regression tests ของทั้งสองบั๊กและรายงานผลแยก simulated/installed/E2E
- Blueprint และบันทึก release ที่อัปเดตตามโค้ดจริง
- รายการเงื่อนไขที่ยังต้องให้ผู้ใช้ช่วย เช่น Login/CAPTCHA/ownership ที่พิสูจน์ไม่ได้ ไม่รับประกันว่าวนสร้างทุกกรณีจนสำเร็จ

บันทึกเพิ่มเติม: ผู้ใช้สั่งลงมือทำหลังอนุมัติแผนแล้ว การแก้ source ได้รับอนุญาต; การติดตั้ง/รีโหลดและทดสอบสร้างจริงยังต้องตรวจเงื่อนไขข้างต้นแยกต่างหาก
