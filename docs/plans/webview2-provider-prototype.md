# WebView2 provider prototype

Branch: `feature/webview2-prototype`. This is a separate future prototype. The current desktop shell already uses WebView2 for SmartFlow's own UI; provider sites still run in Chrome with the Extension.

## Stage 1: isolated read-only lab (implemented on this branch)

`desktop/provider_prototype.py` opens a separate Edge WebView2 window and a separate profile under ignored `build/webview2-provider-prototype/profile-chatgpt`. It does not load the Chrome profile, install an Extension, route a Story job, send prompts, upload files, or read message text. Its page probe records only origin class, readiness, control visibility, and bounded element counts in `events.jsonl`; it records no credentials, full URLs, prompts, or responses. Navigation-time probe errors are retried without logging exception text.

Run `.venv\Scripts\python.exe -m desktop.provider_prototype --smoke` to open and close an offline fixture. Run `--check-provider` to open ChatGPT read-only and close it after page readiness or 30 seconds. Run `--provider chatgpt` for manual inspection in the separate profile; close that window when finished. None of these modes uses a real job.

The source DEV MODE SmartFlow window has an `AI Chat` sidebar page. `desktop/embedded_provider.py` hosts a raw WebView2 control inside the same WinForms window, aligned to the page content. It uses `profile-embedded-chatgpt` under the ignored build folder and does not inject the SmartFlow JavaScript bridge into the provider. Leaving the page hides the control. The old Setup button that launched a second window was removed. The DEV gate hides this menu in the packaged customer app and ordinary browser; the provider control still does not route Story jobs. The native child-control smoke passed (`same_window=true`, `fixture_loaded=true`, `hidden_on_leave=true`), and the reopened source DEV window visibly rendered logged-out ChatGPT inside the SmartFlow page on 2026-10-02. Login and provider workflow were not tested.

## Stage 2: one text request in the embedded page (source DEV only)

The `AI Chat` page has a page probe and a manual text request control. `desktop/webview2_request.py` checks the ChatGPT origin, login, one empty composer, no attachment or generation in progress, and one Send control. It stores an atomic receipt with job/run/request IDs, prompt and conversation hashes, phase, and bounded counts before clicking Send; if a conversation route appears it saves only that owned path for read-only recovery. It verifies a new matching user turn and a stable assistant answer. An ambiguous click or result becomes `needs_review`; another request is blocked to avoid duplicate provider sends. Prompt and answer text stay in memory and are not written to the receipt. The embedded profile requires its own user login. The manual test is separate from real Story jobs and does not upload files, create images, or save Story checkpoints. Source fixtures and native control smoke cover this path; real provider Send and result require live verification.

The owner signed in to the embedded profile. One live, harmless text smoke reached a ChatGPT conversation route, but the adapter marked receipt `WV2-D006CB4E2E224388` as `needs_review` before it could verify the new user turn. The route contains a `:` in its conversation ID; the URL validator rejected it. The validator now accepts that route and records bounded post-click evidence for future failures. Reopening the recent route redirected away from its conversation, so the original Send and answer remain unconfirmed. The receipt remains blocked; the request was not sent again. `tools/smoke_webview2_live_text.py` is an explicit probe/one-send/read-only inspection tool, never part of the automatic test suite. Six request tests, four embedded UI tests, four CLI safety tests, Node DOM fixture, JS syntax, native child-control smoke, and the affected Extension update contract passed after this correction. A successful live provider answer is still required before Story routing.

The owner then confirmed that the first conversation answered `WEBVIEW2_OK`; its original receipt was marked `reviewed_completed` with `verification_source=owner_reported` and archived before the next distinct request. A second one-shot marker `WEBVIEW2_OK_2` passed Send acceptance but stopped when ChatGPT replaced provisional `/c/WEB:...` with a stable `/c/...` route during result collection. The receipt `WV2-5755DCAC313746F5` remains `needs_review`; no retry occurred. The collector now adopts the stable route only after the exact owned user turn is visible there, waits through transient turn disappearance, and records bounded result evidence on failure. Eight request tests pass, including provisional-to-stable route migration. No live automatic result collection is verified yet.

On 2026-10-02, four CLI lab safety tests and four embedded page/native bridge tests passed. The separate CLI read-only ChatGPT check reached `ready=complete`; it did not verify login/session persistence. The embedded page is source DEV only and has not been packaged into the customer SmartFlow executable.
