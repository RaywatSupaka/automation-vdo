# แผนแก้บั๊กโปรแกรมหลักและ Extension ก่อนทำตัวติดตั้ง

วันที่: 27 กันยายน 2026

ฐานหลักฐาน: [รายงานตรวจ 0.15.450](../reports/preinstaller-system-audit-450-20260927.md)

สถานะเอกสาร: แผนเสนอ ยังไม่แก้ production source ไม่เปลี่ยนเวอร์ชัน ไม่รีโหลด ไม่บิลด์

## เป้าหมายและขอบเขต

แก้ 8 กลุ่มบั๊กที่ทำซ้ำได้ พร้อมปิดความเสี่ยง redirect ของ AI Voice ในโปรเจกต์หลัก `C:/Users/keera/Desktop/Shopee_Android_AutoPost` และ `browser_extension/` เท่านั้น เก็บงาน/ภาพ/เสียง/วิดีโอ Final/คิว/ใบรับการส่งเดิมไว้ ไม่ย้อนทั้งโปรเจกต์ไปใช้รุ่นเก่าและไม่เพิ่มฟีเจอร์นอกประเด็น

เมื่อเริ่มลงมือ ให้ตรวจไฟล์และรุ่นปัจจุบันอีกครั้ง ไม่สมมติว่ายังเป็น450 เอกสารสถานะ release เป็นหลักฐานย้อนหลัง ไม่ใช่หลักฐานว่า runtime ที่เปิดอยู่ใช้โค้ดนั้นแล้ว

ตามการตรวจแบบ GET ขณะวางแผน engine37232 ยังมี Story active จึงไม่มีขั้นตอนเปลี่ยน Chrome/โปรแกรมที่กำลังทำงานในรอบนี้

## วิธีทำงานร่วมกันทุกข้อ

1. เก็บ reproduction เป็น regression ที่รันจาก production functions จริง ให้ล้มก่อนแก้
2. แก้เฉพาะจุดเชื่อมที่ผิด พร้อมทดสอบเส้นทางเดิมที่สำเร็จ
3. ไม่ปรับ retry ด้วยการล้างสถานะส่งที่ยังไม่ทราบผล ไม่กด Stop เพื่อทำให้สถานะพร้อม
4. ทดสอบ offline/temp fixtures ก่อน ไม่ใช้คิวหรือไฟล์ผู้ใช้เป็นข้อมูลทดสอบ
5. แยกหลักฐาน source tests, installed Extension และ clean-machine tests; แต่ละชั้นแทนกันไม่ได้

## ระยะ A — ปิดจุดเสี่ยงกับไฟล์และการส่งงานก่อน

### A1. ป้องกันการลบงานที่ยังใช้งาน

จุดแก้: `ui/main_window.py` เส้นทาง Product/Library/worker ลบ, `core/video_library.py`, จุด claim/start ของคิวและงานที่ใช้ไฟล์ร่วมกัน

- รวมการตรวจเป้าหมายลบให้ทุกปุ่มใช้กฎเดียวกัน ไม่ตรวจเฉพาะ UI หรือ bulk delete
- ตรวจ Product/Story/Drama/เรนเดอร์/ปกที่กำลังใช้เป้าหมาย รวมไฟล์อ้างอิงร่วมที่พิสูจน์ได้
- ใช้ lock/operation claim ร่วมกับการเริ่มงาน: ตรวจและจองสิทธิ์ลบในธุรกรรมเดียวก่อนส่ง worker; queue ต้องเริ่มงานที่ถูกจองลบไม่ได้
- ตรวจอีกครั้งก่อนย้ายลงถังขยะ และคืนสิทธิ์ใน finally ทั้งกรณีสำเร็จ/ล้มเหลว
- ไม่ยกเลิกงานอัตโนมัติเพื่อให้ลบได้ งานที่ยังอ้างอยู่ในคิวให้แจ้งเหตุและให้ผู้ใช้จัดการก่อน; ไม่บล็อกงานเสร็จที่ไม่เกี่ยวข้องโดยไร้เหตุ

เกณฑ์ผ่าน:

- active job → ไม่เรียก recycler แม้แต่ครั้งเดียว
- เปิด confirmation ก่อนเริ่มงาน แล้วค่อยยืนยัน → ยังลบงานที่เริ่มไปแล้วไม่ได้
- กดยืนยันซ้ำ → deletion worker ไม่ทำซ้อน
- ลบงานเก่าที่ไม่ใช้งานได้ตามเดิม; bulk รายงานรายการที่ข้าม/ล้มเหลวตรงความจริง
- Start/Delete ชนกัน → ได้สิทธิ์เพียงฝ่ายเดียว ไม่มีไฟล์หายกลางรัน

### A2. แก้ Meta ใช้ปุ่ม/พิกัดเก่าหลังรอ ACK

จุดแก้: `browser_extension/src/platforms/meta-ai/video.js` เส้นทาง ready_to_send และคลิกจริง รวมสัญญาใบรับกับ desktop เฉพาะถ้าจำเป็น

- หลังบันทึก send intent และรับ ACK ให้ตรวจ tab/document/request/owner เดิมอีกครั้ง
- ตรวจพรอมต์และภาพแนบตรงคำขอ, ไม่มี Stop/งานกำลังสร้าง, ปุ่มส่งเปิดใช้และ hit-test ตรงเป้าหมาย
- ตรวจตอนก่อน mouse press และระหว่าง press/release ไม่แก้เพียงเพิ่มการอ่าน DOM อีกครั้งก่อนรอรอบใหม่
- ถ้าหน้าเปลี่ยนก่อนกด ให้ไม่คลิกและบอกเหตุที่ตรงหลักฐาน; ถ้ากดไปบางส่วนแล้ว ให้เก็บสถานะผลไม่แน่ชัดและอ่านผลต่อ ไม่ reset intent เพื่อยิงซ้ำ
- หากต้องปล่อยเมาส์จาก gesture ที่เริ่มแล้ว ให้ไม่เลื่อนปล่อยลงปุ่ม Stop/ปุ่มอื่นและไม่ทำ gesture ใหม่เอง

เกณฑ์ผ่าน: ACK ช้า+แก้ร่าง/เปลี่ยน Stop/ย้ายปุ่ม/เปลี่ยนหน้า/ยกเลิก ต้องไม่คลิกผิด; กรณีปกติส่งครั้งเดียว; ไม่ทำให้ choice follow-up หรือ receipt recovery เดิมถอยหลัง

### A3. รักษาตัวเลือกสินค้าตั้งแต่ก่อนเข้า Shopee จนเข้าคิว/AI

จุดแก้: `web_ui/product_story.js`, ตัวรวมค่าเสียง/Flow/ปก/Intro/Green และสัญญา preparation ที่ backend

- สร้าง snapshot ของทุกตัวเลือกจากฟอร์ม Product ที่ผู้ใช้กด ก่อนเริ่ม capture
- snapshot ระบุที่มาฟอร์มและ schema; normal submit อ่าน controls ครั้งเดียว ส่วน handoff/resume ใช้ค่าที่บันทึกไว้
- wrapper ทุกชั้นต้องเคารพ snapshot ไม่เลือกหน้า Story จาก mode ที่ใช้ส่งต่อภายใน
- เปลี่ยนหน้าหรือปรับค่าอื่นระหว่างรอ Shopee ต้องไม่แก้งานที่ส่งไปแล้ว
- งานเก่าที่ไม่มี marker ใช้เส้นทาง compatibility ที่ตรวจจากค่าของงานเอง ไม่ตีความข้อมูลหายเป็นอนุญาตอ่านฟอร์มปัจจุบันทับ
- ไม่ใช้แค่เงื่อนไขว่ามี field อยู่แล้วกับทุก request เพราะอาจทำให้การสร้างงานใหม่ไม่อ่านค่าที่ผู้ใช้เพิ่งเปลี่ยน

เกณฑ์ผ่าน:

- direct/batch/resume ได้ค่าเหมือน snapshot ก่อน capture ทั้งเสียง ซับ ปก Flow Intro Green และค่าผู้ให้บริการที่เกี่ยวข้อง
- ตั้ง Product ต่างจาก Story แล้วยังไม่ปนกัน
- เปลี่ยนฟอร์มระหว่างรอ capture ไม่เปลี่ยน payload/checkpoint/queue/package ของงานนั้น
- เส้นทางสร้าง Story/Drama/Long ปกติยังอ่าน controls ของตนตามเดิม
- ใช้ wrapper stack ตามลำดับ script จริงใน index.html ไม่ทดสอบไฟล์เดี่ยวอย่างเดียว

## ระยะ B — แก้การกู้ปกและ controls ที่ใช้งานไม่ตรงกัน

### B1. กู้ภาพปกหลัง retry ได้โดยไม่สร้างซ้ำ

จุดแก้: cover collector/reference owner ใน `browser_extension/chatgpt.js`, หลักฐานคำขอใน `core/ai_cover.py` และ background เท่าที่จำเป็น

- เก็บความสัมพันธ์ original reference turn → accepted retry turn → result owner อย่างถาวร ก่อนพึ่ง collector อ่านผล
- เมื่อ collect-only ให้ตรวจความสัมพันธ์นี้ใน conversation เดิม ไม่บังคับให้ retry turn ต้องแนบรูปใหม่
- ห้ามค้นชื่อไฟล์ทั้งแชตแล้วรับรูปจากคำตอบใดก็ได้ ห้ามเปลี่ยนภาพอ้างอิงเป็นภาพผลลัพธ์
- คำขอเก่าที่ไม่มีหลักฐาน ให้รับเฉพาะเมื่อพิสูจน์ความสัมพันธ์เดิมได้ ไม่สร้างใบรับย้อนหลังจากการเดา

คงคำสั่งผู้ใช้เรื่องปก:

1. มีหลายภาพที่ใช้ได้ → เลือกหนึ่งภาพแล้วดาวน์โหลด ไม่รอผู้ใช้เลือก
2. ดาวน์โหลดภาพนั้นไม่สำเร็จจริงหลังการลองเก็บไฟล์เดิม → ขอปกใหม่หนึ่งภาพ ไม่มีตัวเลือก
3. AI ยังสร้างอยู่ → รอ ไม่กด Stop/ไม่ส่งซ้ำ

เกณฑ์ผ่าน: ขัด collector หลัง accepted retry แล้วกู้ภาพได้โดย extra Send=0, extra upload=0; wrong request/reference/newer user ต้องปฏิเสธ; ทดสอบสองภาพและ download replacement450 เดิมยังผ่าน; Final ไม่เปลี่ยน

### B2. ทำ Cover Studio ให้ข้อกำหนดตรงกับสิ่งที่ผู้ใช้เห็น

จุดแก้: `web_ui/clip_cover.js`, `core/ai_cover.py`, พรอมต์ cover เฉพาะคำขอใหม่

ข้อเสนอ UX ในแผนนี้:

- ปกทำเองคงรับได้60ตัวอักษรตามเดิม
- ปก AI คงกติกา40ตัวอักษร แต่แสดงข้อจำกัดและตรวจให้ชัดก่อนส่ง ไม่ให้ดูเหมือนรับ60แล้วค่อย error ทีหลัง
- เมื่อผู้ใช้ระบุข้อความสำหรับปก AI ให้ส่งข้อความนั้นไปจริง; ถ้าว่างจึงใช้ชื่อคลิปให้ AI ออกแบบ
- ไม่ตัดข้อความอัตโนมัติ ไม่เปลี่ยน prompt หรือ matching ของคำขอเก่า และไม่ย้ายข้อความจากฟอร์มสร้างงานที่ตั้งใจซ่อนไว้
- กำหนดวิธีนับตัวอักษรให้ frontend/backendตรงกัน รวมไทยและemoji ไม่ใช้JS string.lengthกับPython lenโดยถือว่าเท่ากันทุกข้อความ

เกณฑ์ผ่าน: ข้อความกำหนดเองถึง prompt ใหม่, 40ผ่าน, 41/60ได้คำอธิบายเฉพาะปุ่ม AI โดยปกทำเองยังใช้ได้; ค่าว่างใช้ชื่อคลิป; collect-only เก่าไม่เสีย

### B3. ละครโหมดผู้บรรยายใช้ auto_cast ได้จริง

จุดแก้: submit validation ใน `web_ui/storytelling.js` ให้ตรง `core/drama_series.py`

เกณฑ์ผ่าน: ทดสอบ Create และ Enqueue ตั้งแต่ UI wrapper ถึง backend สำหรับทุกโหมด; narrator0ผ่าน, solo0/visual0/dialogue1ยังไม่ผ่าน; งานเดิมไม่ถูกสร้าง cast ซ้ำ

## ระยะ C — เตรียมเส้นทางอัปเดตเครื่องลูกค้าให้ปลอดภัย

### C1. อ่าน JSON ภาษาไทยด้วย UTF-8

จุดแก้: `tools/customer_updater.py` config/release/journal/ready-marker ที่โปรแกรมเขียนเอง

- ระบุ encoding='utf-8' สอดคล้อง writer ไม่พึ่ง Windows locale
- แยก config อ่านไม่ได้กับ EXE ใหม่เปิดไม่สำเร็จ; ไม่ทำ rollback เพราะอ่านภาษาไทยผิด
- รักษา rollback เมื่อ binary/launch verification ล้มจริง

เกณฑ์ผ่าน: Windows UTF-8 on/off, ชื่อบัญชี/พาธ/ค่าตั้งภาษาไทยและอังกฤษ, updateสำเร็จ, corrupt configและlaunch failureรายงานตรงเหตุพร้อมเก็บข้อมูล

### C2. แจ้งสถานะ Extension หลัง desktop อัปเกรดให้ตรงจริง

จุดแก้: `core/customer_runtime.py`, `core/extension_identity.py`, bridge heartbeat, background/popup และหน้าสถานะที่แสดงผล

- แยก engineเปิดอยู่ / ยืนยันExtensionแล้ว / รุ่นไม่ตรง ไม่แสดงว่าใช้งานพร้อมเพียงเพราะ /healthตอบ
- ให้รุ่นเก่าเห็นเลขรุ่นที่ต้องอัปเดตผ่าน diagnostics แบบอ่านอย่างเดียว แม้ยังไม่มีสิทธิ์รับคำสั่งงาน
- หากต้องใช้ทะเบียน permanent installation ให้ตรวจ identity/path/hash/provenance ไม่เชื่อจากชื่อหรือIDที่ผู้เรียกบอกเอง
- รักษาโฟลเดอร์ที่Chromeโหลด, ID, profileและreceipts; ไม่ถอนติดตั้ง ไม่คัดลอกprofile/credentials และไม่overwrite/reloadขณะ active
- การยอมให้แจ้ง mismatch ไม่ใช่การอนุญาตให้ Extensionเก่าส่งผลหรือรันงานด้วยสัญญารุ่นใหม่

เกณฑ์ผ่าน: fresh install, A→BโดยExtensionยังA, ไฟล์บนดิสก์เป็นBแต่ChromeยังโหลดworkerA, แจ้งวิธีแก้ได้และไม่dispatch, อัปเดตไฟล์ในpathเดิม+Reloadแล้วจับคู่Bได้, Extensionปลอมยังไม่ได้สิทธิ์

### C3. ป้องกัน AI Voice ส่งคีย์ตาม redirect ข้ามปลายทาง

จุดแก้: `core/external_tts.py` JSON และ download transport

- ตรวจ redirect ก่อนส่ง requestใหม่; ปฏิเสธข้าม HTTPS originที่อนุญาตและการลดเป็นHTTP
- ถ้าจะอนุญาต same-origin ให้มีข้อจำกัดจำนวน redirect และไม่เปลี่ยนวิธีส่งที่ทำให้สร้างเสียงซ้ำ
- เก็บการจัดการ timeout/อ่านงานเดิม/idempotencyและการดาวน์โหลดไฟล์ชั่วคราวตามเดิม

เกณฑ์ผ่าน: ใช้คีย์สังเคราะห์ ตรวจ JSON/download + cross-host/downgrade ไม่ส่งคีย์ออก, same-originตามกฎที่กำหนด, ไม่ทำ requestสร้างงานซ้ำ ความเสี่ยงนี้ไม่ใช่หลักฐานว่าบัญชีผู้ใช้เคยมีคีย์รั่ว

## ระยะ D — รวมและทดสอบก่อนเปิดให้ใช้

### D1. Source/fixtures

- รัน regressionใหม่ของA/B/Cและเส้นทางปกติข้างเคียง
- เพิ่ม integrationตามจุดเชื่อมจริง: UI→snapshot→job/queue→package, DOM→intent→gesture→receipt, retry→restart→collect, update→identity→mismatch
- จำลอง ACKช้า/ซ้ำ, เปลี่ยนหน้า, ยกเลิก, ไฟล์หาย, processขัดจังหวะ และเจ้าของงานเปลี่ยน
- หลังโค้ดนิ่ง รัน full suiteหนึ่งรอบและ JS syntax; ทุก skipต้องอธิบาย ไม่เอาจำนวนผ่านแทนหลักฐานการทดสอบที่ขาด

### D2. รุ่นและการเปิดใช้บนเครื่องนี้

- กำหนดรุ่นใหม่เมื่อจะส่งมอบหลังแก้เสร็จ ไม่ทับartifact450และไม่รีบกำหนดเลขหากมีงานอื่นอัปเดตไปก่อน
- sync manifest/desktop required version/helper build/release metadata/blueprints ที่เกี่ยวข้อง
- เก็บExtensionใหม่ในdeliverablesและเทียบทุกไฟล์กับcanonical source; ไม่บิลด์installerในขั้นนี้
- ตรวจว่าไม่มีงาน active ก่อนเปิดโค้ดใหม่ ผ่าน canonical `SmartFlow AI.exe`; รักษาExtension path/ID/profileเดิม
- แจ้งผลแยกว่าผ่านsourceแล้วหรือได้ทดสอบinstalledจริงแล้ว ไม่เหมารวม

### D3. Installed smoke และเครดิต

- ทดสอบเปิดหน้า/controls/queue/settingsโดยไม่Generateก่อน เมื่อไม่มีงานผู้ใช้รันอยู่
- ทดสอบ Productผ่านShopeeถึงAI, Coverเลือกหนึ่งภาพ/กู้หลังretry, Metaส่งครั้งเดียว, narratorDrama, Story/Long compatibilityผ่านSmartFlowจริง
- ใช้ภาพ/คลิปเดิมสำหรับทดสอบปลายทางที่ไม่ต้องเจนใหม่
- การสร้างภาพ/วิดีโอจริงให้กำหนดจำนวนและการอนุญาตแยก ไม่เอาคำสั่งวางแผนนี้ไปใช้เครดิต
- ปิดเฉพาะทรัพยากรทดสอบที่เปิดเอง และตรวจพอร์ต/โปรเซสทดสอบปิด โดยไม่หยุดงานผู้ใช้

## เงื่อนไขก่อนทำตัวติดตั้ง

1. ไม่มีP1ที่ยังไม่แก้ และ regressionของ8กลุ่ม+redirectผ่านตามขอบเขตที่ตกลง
2. Main source/Extension/metadataและไฟล์ส่งมอบตรงกัน
3. ทดสอบinstalled workflowที่จำเป็นจริงแล้ว พร้อมบันทึกส่วนที่ยังไม่ได้ทดสอบ
4. ผู้ใช้สั่งบิลด์แพ็กเกจทดสอบ จึงสร้างinstallerเพื่อลงWindowsสะอาด ไม่มีPython/dev PATH ทั้งชื่อบัญชีไทยและอังกฤษ
5. ตรวจfresh install, WebView2/Chrome pairing, media tools, updateA→Bพร้อมงานเดิม, rollbackและuninstallเก็บข้อมูล ก่อนระบุว่าพร้อมแจก

การผ่านsource testsอย่างเดียวไม่รับรองclean-machine readiness ขั้นตอนสร้างแพ็กเกจทดสอบมาก่อนทดสอบเครื่องสะอาดได้ แต่ไม่เรียกแพ็กเกจนั้นว่ารุ่นพร้อมแจกจนกว่าจะผ่านเกณฑ์

## สิ่งส่งมอบหลังได้รับคำสั่งลงมือ

- โค้ดแก้เฉพาะจุดในโปรเจกต์หลักและExtensionหลัก
- regressionที่แสดงกรณีเดิมพังและกรณีแก้แล้วผ่าน รวมขอบเขตไม่ให้ส่งซ้ำ/ลบงานที่ใช้/ทับค่าที่เลือก
- รายงานผลจริงและข้อจำกัดแยกตามระดับการทดสอบ
- Extensionรุ่นใหม่ในdeliverablesเมื่อพร้อมส่งมอบ; installerจะทำตามคำสั่งแยกภายหลัง
